> 下文的独立摘要存储、后台维护及相关迁移建议不再作为当前实施要求。

范围：会话上下文、滚动摘要、历史召回、用户长期记忆及其数据生命周期。

## 1. 总体决策

每轮模型输入由以下内容组成：

> 系统规则 + 当前问题 + 当前有效条件和用户画像 + 历史摘要
> + 近期双方对话 + 按需召回片段 + 本轮相关工具事实。

核心要求：

1. 数据库存完整历史，模型只读有预算的上下文；二者分开。
2. 意图识别、规划、回答共享同一个会话基础快照，分别追加任务资料。
3. 旧消息先被成功摘要覆盖，再退出常驻原文窗口；失败不能伪造覆盖。
4. 用户条件、历史助手说法、工具事实分别标注来源和适用范围。
5. 工具资料独立限额，不随聊天轮数持续堆积并挤掉近期对话。
6. 长期画像显式确认后更新；摘要不能自动写回画像。
7. 身份隔离、执行归属、幂等、确认写入及持久化错误处理继续保留。
8. 规则精简后按预算占用比例触发压缩；压缩目标不是必须达到的事实或安全条件。

沿用现有 Python、LangGraph、FastAPI、React/TypeScript、MCP 和数据库。
不新增记忆微服务、向量库或记忆框架，不重做已验收的直接回答链路。
已有 Qdrant 菜品检索不承担本期聊天记忆检索。

## 2. 当前实现与实际缺口

以下是本轮源码核对结果，不是新增运行验收：

| 位置 | 已有能力 | 本次要处理的问题 |
| --- | --- | --- |
| `application/chat_service.py` | 承接上一轮槽位、消息、菜品及证据 | 从 checkpoint 复制并裁剪消息，不能代表完整历史 |
| `memory/context.py` | 槽位合并、近期文本拼接截断 | 没有滚动语义摘要；列表累加不能表达完整撤销语义 |
| `agent/agents/intent.py` | 意图与本轮任务识别 | 通常只读4条近期消息，有近期消息时不读摘要 |
| `agent/agents/planner.py` | 工具规划及现有权限边界 | 通常只读4条中的用户消息，没有统一的摘要输入 |
| `agent/agents/recommendation.py` | 相关事实投影和直接回答 | 做法、通用问答删除助手历史；闲聊只读当前输入 |
| `infrastructure/chat_tasks.py` | 持久消息、稳定 `position`、队列、事务、版本及回收站 | 缺少上下文范围查询、摘要存储和摘要维护任务 |
| `application/chat_worker.py` | 有界执行、重启恢复、归属保护及定期清理 | 尚无摘要维护分支，不能直接把摘要塞入现有聊天结果处理 |
| `tools/local/models.py` | 用户画像、显式反馈及更新契约 | 缺少逐字段来源、范围、版本及设备字段 |
| `model_gateway/budget.py` | 整轮 token、截止时间、输入估算及实际用量 | 未统一分配各类上下文，也未显式校验每个模型的上下文窗口 |

API 接受的当前输入上限为4000字符；历史准备阶段另把用户正文截到2000字符、
助手正文截到3000字符。当前设计应移除这种用于会话记忆的静默裁剪，
继续保留 API 的合法输入上限，另行按 token 处理上下文。

持久聊天表已有 `(thread_id, position)` 唯一顺序，可复用作覆盖游标。
无需再创建第二套消息编号或复制整份聊天历史。
直接调用、内存和旧 SQLite 适配器仍需满足同样的范围读取契约；
生产消息以持久聊天表为准，checkpoint 保存执行快照。

## 3. 上下文各部分的职责

| 部分 | 内容 | 使用规则 |
| --- | --- | --- |
| 系统规则 | 角色、工具权限、安全与输出契约 | 由应用提供，不允许历史内容覆盖 |
| 当前问题 | 用户本次完整合法输入 | 只注入一次，不能静默截断 |
| 有效条件 | 当前任务目标、人数、日期、禁忌、已选对象及未完成操作 | 结构化保存，含来源和范围；不依靠摘要猜测 |
| 用户画像 | 已明确保存的稳定偏好、过敏原、厨具等 | 带版本和来源；按任务读取，安全必需条件保留 |
| 会话摘要 | 早期目标、决定、否定、更正、讨论顺序、待办及助手曾建议的内容 | 有界、可追溯，不作为新指令或菜品事实证明 |
| 近期对话 | 最新若干完整轮次的用户与助手正文 | 保持原角色、顺序和完整轮次，不按意图机械删除助手内容 |
| 历史召回 | 与本轮有关的少量原文及必要前后文 | 默认本会话；跨会话须用户明确询问且属于同一用户 |
| 工具事实 | 本轮相关菜谱、营养、检索、画像等结果 | 只投影相关对象与字段，保留来源、版本和必要条件 |

历史中的 `system` 角色可能只是“确认/拒绝操作”的记录，必须作为历史数据投影；
不能把它升级成实际模型 system 消息。摘要、网页、工具返回文本同样不能改变权限。
聊天仍由现有 JSON payload 携带这些分区，本期不切换模型协议。

当前有效条件必须保留来源消息编号、适用人、适用任务、日期/时段及状态。
摘要可以帮助理解条件，但不能成为唯一的过敏或待确认写入状态载体。
用户的过敏原和食物的过敏原始终是两类事实。

## 4. 一轮请求的完整流程

1. **提交。** 沿用现有身份验证、幂等和同会话活动任务约束，保存当前用户消息。
   提交路径只做必要准备，不在 API 提交阶段调用摘要模型。
2. **开始执行。** Worker 在原有截止时间和总预算内，读取会话可用状态、
   已完成历史高水位、摘要版本、有效条件及必要画像版本。
   当前问题单列，历史范围只到它之前，避免重复注入。
3. **读取基础上下文。** 从持久消息按位置反向选取最新完整轮次，
   再正序组装。补上摘要游标之后尚未覆盖的历史，明确是否完整覆盖。
4. **评估比例及必要时补压缩。** 规则精简后达到80%软阈值时，
   先判断旧原文是否可压缩、节省是否足以抵消压缩成本。
   预计超过硬上限时，可等待已有维护任务在本轮期限内完成，
   或抢占一个有持久记录的有界补压缩任务；同一会话不可重复并行压缩。
   前台最多一次补压缩尝试，不能在请求内无限追赶历史；
   仅到软阈值而尚可安全执行时可调度后台，不必阻塞当前回答。
5. **冻结基础快照。** 保存 `context_version`、摘要版本、原文范围、画像版本、
   有效条件版本和来源编号，供本轮重试及恢复使用。
6. **意图识别。** 使用基础上下文理解当前任务、对象及指代。
   若明确依赖早期原文，执行有界历史召回；因召回才澄清任务时，
   最多补做一次意图识别，不能无界循环。
7. **规划和工具执行。** 沿用现有工具循环；按对象编号取当前事实，
   新工具结果追加到本轮证据区，不把所有历史工具结果重放。
8. **生成和发布。** 回答阶段使用同一基础上下文及本轮相关证据，
   保留现有结构、事实与安全硬检查，沿用当前直接回答策略。
9. **提交结果。** 沿用执行版本保护，事务保存消息、结果和状态；
   根据完成后的历史及保守的下一轮开销预测检查80%软阈值，
   同一事务持久记录维护需求或待评估标记，避免“回答已保存但维护任务永久丢失”。
10. **后台维护。** Worker 在用户聊天任务之外，以低优先级处理摘要；
    具备独立上限和持久化状态，重启后继续。

基础快照不因摘要后台更新而在一轮中途被替换。按需召回属于附加上下文，
记录增补版本和来源，后续阶段可见；发生任务理解变化时重新判定，
不让回答阶段独自读取一份意图阶段完全未知的新历史。

工具执行后及每次模型调用前都重新计量。若必须在本轮中途补压缩，
只能针对同一已冻结历史高水位重新表示资料，显式生成上下文增补版本，
保留有效条件、来源范围、当前任务和已确定的对象，不暗中换入新会话内容。
压缩改变任务理解时回到现有有界意图/规划路径，仍受总预算和调用上限约束。
后台摘要不强制刷新本轮基础快照；是否采用新版本由执行方校验并记录。

数据库画像更正在本轮期间发生时，发布前检查画像/有效条件版本。
安全相关条件已变则按现有重试与截止时间重新规划或终止该轮，
不能明知版本过期仍发布。普通偏好变更可下一轮生效并记录版本。
会话已入回收站或任务已失去执行归属时，停止读取和提交。

## 5. 近期原文窗口

初始目标为最近6个完整对话轮次，作为调参起点，不是硬编码保证。
一个轮次包括该次用户输入、用户实际看到的助手输出，以及关联的确认结果；
不能简单把12条消息当作6轮，确认流程会产生额外消息。

- 依据消息编号、持久位置和运行关联归组；旧消息不能可靠归组时保守保留并标记。
- 从最新轮次向前取，最终正序发送；不能正序取前若干条而漏掉最新对话。
- 进行中的用户输入单列；失败、取消及待确认状态如实保留，不能总结为已成功。
- 澄清问题和用户回答一起保留，不能再用追问文本覆盖整份会话摘要。
- 待确认操作继续以 checkpoint/持久任务的真实状态为准，摘要无权批准操作。
- 已摘要消息通常不再重复注入原文；本轮需要精确措辞时可通过召回补取。

6轮是目标保留尾部。后台压缩尚未完成时，尚未覆盖的尾部可能暂时超过6轮；
预算允许则完整保留，不能为了凑窗口直接丢掉中间部分。
低于比例阈值时可保留更多尚未压缩轮次，6轮不代表读取上限。
达到阈值先压缩6轮之前的旧前缀；若仍超硬上限，
可在一次有界前台任务内选更长的旧前缀并减少原文保留轮数，
前提是完整轮次被成功摘要覆盖、当前问题和安全条件完整、
最新一组可辨认的问答/确认依赖仍可用，且实际保留轮数有记录。
无法满足时澄清或有界结束，不强行满足6轮或60%的数字目标。
遇到单条超长助手回答或历史迁移的大消息，可将它作为单独可追溯片段处理，
但摘要仍只能在完整轮次/安全事务边界推进，不能把半条消息当成完整覆盖。

## 6. 滚动摘要

### 6.1 内容格式

使用 Pydantic 校验的有界结构化摘要，包含：

- `goals`：目标、日期、人数及适用对象。
- `decisions`：已选、拒绝、替换及撤销的决定。
- `references`：菜品编号、实际展示顺序、关联轮次及配方版本引用。
- `open_items`：尚未解决的问题和待澄清点。
- `assistant_notes`：助手曾解释或建议过什么，明确属于助手说法。
- `corrections`：用户更正、被替代条件及其来源。

条目附来源消息编号和适用范围。不能确认的内容保留不确定状态；
不把用户推测变成食品事实，也不把助手建议变成用户决定。
摘要只保留必要对象引用，营养数值和完整配方优先回工具查询。
摘要长度固定有界；关键有效条件单独保存，不能因为摘要超长而移除过敏等限制。

### 6.2 触发与覆盖

建议初值：先规则精简，预计输入达到可用输入额度80%时触发维护决策，
以降至60%左右为目标；额度与占用公式、执行位置和例外见第10.2节。
保留最近6轮为目标，选择较早的连续完整前缀压缩；
具体范围按预计节省、压缩输入额度和时间选择，不为凑固定轮数反复压缩。
单批起步最多4轮；足以达标则停止，不足时后台可续后续批次，
前台仍最多一次尝试。软阈值无需承诺一次达到60%。
超过8轮只提示重新计量和检查积压；占用低且无其他需求时不强制摘要。
以上均为待验证参数，摘要过程本身也须能装入维护任务的模型窗口和预算。

模型输入为“旧摘要 + 旧游标之后的一段连续原文 + 当前有效条件及更正”。
新摘要融合旧摘要，而不是只总结本次输入或在旧摘要后无限追加文本。
来源编号必须来自旧摘要已有来源或这次明确读取的原文；
程序校验来源合法、覆盖范围连续、输出结构和额度有效。
这些检查不能证明摘要语义无遗漏，仍需真实对话验收和原文召回。

摘要成功须满足：生成成功、结构和来源校验通过、版本检查通过、
摘要与覆盖游标在同一事务提交。否则保持旧版本与游标不动。

### 6.3 并发算法

1. 读取版本 `V`、历史变更代号 `E`、覆盖位置 `C`，
   选择已完成且可安全压缩的连续范围 `(C, T]`。
2. 事务外调用模型，不能持有数据库长事务等待网络。
3. 提交时重新检查归属、会话可用状态、`E`、`V` 和 `C`。
4. 条件更新成功后，同事务保存新摘要、`covered_through=T`、`version=V+1`
   及任务完成状态；条件不匹配则放弃旧结果并重新排队。
5. 新消息仅追加到 `T` 之后不必让本任务失效；历史重写、删除或来源失效会使 `E` 改变。

覆盖游标表示处理过的原文范围，不代表其中每一个语义细节都保留了。
摘要不会物理删除聊天原文。模型压缩失败、超时和进程崩溃均不得推进游标。

### 6.4 对话示例

假设最早用户说“今天做两人晚餐，不放香菜”，助手推荐A、B、C；
之后查B的做法，再聊通用烹饪问题，最终这些轮次退出近期窗口：

- 有效条件保留当天、晚餐、两人和不放香菜的来源与范围。
- 摘要记录A/B/C的展示顺序和曾讨论B，配方只留对象/版本引用。
- 近期窗口保留最新双方原文，不因为转成通用问答而删除助手回答。
- 再问“第二道怎么做”时，找回对应展示轮次和B的编号，再查询B的配方。
  若后来又展示过另一组菜，先依据指代上下文判定；不确定则澄清。
- 用户说“香菜可以放了”，撤销本餐条件；旧摘要不能再次激活该限制。
- 第二天新建会话不会自动继承昨天的临时人数、餐次和香菜条件。

## 7. 历史召回

首期用现有数据库的按位置、时间、关键词和对象编号查询，不引入新检索服务。
中文查询按短语和已识别菜名检索，避免仅按空格分词；SQL 条件参数化并转义通配符。

召回分两种入口：

- 自动入口：用户提到“之前那个”“第二道”“刚才的限制”等，
  基础上下文缺少对应原文，或规划阶段发现无法确定引用对象。
- 显式入口：用户要求查早期说法、某天讨论、其他本人会话。

优先顺序为精确消息/菜品引用、当前会话匹配、时间与关键词匹配；
排序后去重，补相邻轮次，再按总额度裁剪完整片段。
建议起步最多3组片段、合计约1200个估算输入 tokens，片段数量和额度均可调。
片段带会话编号、消息编号、位置、时间、角色和命中原因。
只读历史查询不触发写入确认，但必须经过用户归属和回收站检查。

向模型暴露一个有界只读历史查询能力，落在现有工具权限和执行预算之内；
会话内精确引用可由程序直接查询，不要求每次额外模型规划。
同一查询本轮去重；未找到时明确没有找回，不能编造历史。

摘要支持大意理解，召回处理精确措辞和细节。若问“当时说了多少”，
可以引用当时原文并标注它是历史说法；若问当前真实营养或做法，
仍需原始工具核实，历史助手正文不能替代事实证据。
用户明确比较新旧配方时同时保留版本，不能用最新数据冒充历史版本。

跨会话默认关闭；仅在用户明确询问其他本人历史时临时开放查询范围，
返回必要片段，不把所有旧会话自动拼入当前问题。
关键词召回不承诺覆盖所有同义转述，检索不确定时继续澄清。

## 8. 有效条件、槽位与长期用户记忆

### 8.1 作用域与操作

区分本次请求、本会话、指定日期/餐次/人员、用户长期画像。
临时范围不明时先限制在当前会话，不擅自永久保存。
“今天”按用户配置时区解析成具体日期，跨日后不能继续当作今天生效。

槽位更新采用字段级 `set`、`add`、`remove`、`clear`，以已校验补丁表达；
程序校验字段白名单、类型、目标范围、来源及执行权限。
不再把空列表统一忽略，也不把所有新列表一律并入历史。

例子：

- “今天不吃辣”建立今天的条件，不改长期偏好。
- “不吃香菜了”若仅指当前餐，更新对应任务；若要长期保存则进入确认。
- “取消刚才的热量上限”清除对应临时条件，不写成0或重新带回旧值。
- “这是给朋友的”切换适用人，不修改本人画像；不能在对象不明时无条件解除安全限制。

约束合并按字段规则执行，不能统一采用“最后一句话覆盖一切”。
当前明确请求可覆盖普通口味偏好；已保存过敏信息不能被“随便推荐”或摘要隐式清除。
用户明确更正过敏信息时走画像确认，冲突未解决前不能推荐已知风险对象。
食品自身含某过敏原不推出用户过敏，用户曾拒绝一道菜也不推出其所有食材都不能吃。

### 8.2 长期记忆的保存与管理

长期信息继续以 `UserProfile` 和显式反馈为主，不另建一份平行偏好库。
画像补充逐字段来源类型、来源引用、更新时间及版本；
厨具确有需求时补到画像模型、更新契约、API 和现有画像页。
历史反馈的“不喜欢某道菜”保留原含义，不扩写成疾病、过敏或永久食材禁令。

- 画像页保存沿用当前预览确认。
- 聊天中明确要求长期保存时，生成结构化变更预览，复用已有确认执行机制；
  当前工具是否支持该操作要在实施时补齐，不能宣称现已具备。
- 摘要维护任务只写会话摘要，无画像写权限。
- 不从每次聊天自动批量收集并永久保存隐含个人信息。
- 显示、修改、清空长期记忆走现有画像入口，展示必要来源和更新时间。

### 8.3 更正和“忘记”

画像记录递增版本，并按字段保留来源截止/失效标记，避免旧后台任务覆盖新更正。
已撤销来源不能自动生成新画像或重新激活旧会话条件。
会话里的更正要同时更新有效条件，摘要下一次维护保留更正关系。
旧原文可能仍存在，但读取时必须结合当前版本和撤销状态，不按旧话重新合并条件。

区分三种用户请求：

- 取消本轮限制：更改临时条件。
- 删除已保存偏好：删除画像对应值并使旧提取来源失效。
- 删除相关聊天记录：按会话删除流程处理；若要求更细粒度原文清除，
  另补来源重建与删除实现，不能把“删画像”等同于“已清除全部历史”。

来源元数据只保留必要引用和版本，不在撤销标记里复制被删除的敏感正文。
独立保存的画像不会因删除来源会话而自动消失；
来源显示为不可用，不再解引用已删除原文。若用户明确要求连画像一起删除则一并执行。

## 9. 工具资料投影与版本

持久化保留现有工具执行和来源记录；上下文只注入本轮所需内容。
已有 `answer_evidence`、`compact_tool_results` 和菜品查询优先复用。

| 场景 | 应进入本轮证据的资料 |
| --- | --- |
| 推荐几道菜 | 本轮真实候选、必要营养和来源，另带已展示对象顺序引用 |
| “第二道怎么做” | 对应菜品的配方原文、必要用量和条件 |
| “这两道哪个脂肪低” | 两个明确对象、可比较口径和相关营养范围 |
| 通用烹饪原理 | 必要参考和当前操作状态，移除无关候选菜谱 |
| 查询画像或更改偏好 | 当前画像版本和相关字段，不注入全部菜谱 |

去重键包含工具名、对象、参数、来源及可用版本。
同对象不同配方假设、可选配料或份量不是可随意覆盖的重复项。
无显式版本时使用内容指纹辨别变化，同时标明没有可查询的历史版本保证。
保存已有工具结果引用或必要来源快照，不为上下文再复制全套工具日志；
未持久保存的历史配方版本不能声称可恢复。

不能为压缩删除单位、整菜/每份口径、范围、可选食材、估算标识及来源。
大结果先按目标对象筛选，再分批/按需读取；
单道配方仍过大时，完整必要字段分片整理或明确材料未读全，不用省略号冒充全量配方。
工具失败明确保留失败状态，不把旧成功结果冒充当前成功。

## 10. Token、时间与费用预算

必须同时满足：

```text
单次请求：
  系统规则 + 输出结构/工具定义 + 当前输入 + 有效条件/画像
  + 摘要 + 近期原文 + 召回 + 工具资料 + 输出预留 + 估算余量
  <= 当前所选模型的上下文窗口

整轮请求：
  已累计使用 + 预计后续意图/规划/生成/修订/重试/前台补压缩的输入与输出
  <= 本轮总 token 预算，并满足原截止时间
```

现有默认整轮预算为24000 tokens、90秒；本方案不默认上调。
单次模型窗口要单独配置并核对实际模型，不能把整轮24000当作模型窗口，
也不能假定主模型和备用模型窗口相同；切换备用模型须重新检查可容纳性。
这里不填写未经官方配置核对的模型窗口数字。

复用 `ExecutionBudget` 和提供方实际 usage 校准估算。
计入真实序列化内容、schema、反馈及失败重试，字数或消息条数不能等价当作 tokens。
若有匹配的现成 tokenizer 可使用；本期不为此强制添加依赖。

装配前先预留当前问题、安全必需条件、输出及剩余必要调用；
再为共同基础上下文确定额度，最后给工具和召回分配独立额度。
各阶段追加的工具定义不同，公共基础额度按所需阶段最紧的约束计算。
不是每个阶段各自随意裁剪同一段历史。

超额顺序：

1. 去掉重复字段、无关候选、可恢复的大段工具说明和不必要召回。
2. 按当前任务缩小工具对象集合，必要时分批读取。
3. 压缩已经达到退出条件的旧完整轮次，维持近期对话空间。
4. 仍不足时读取最相关原文和最新完整尾部，明确记录缺失区间；
   需要缺失信息才能安全回答时澄清或有界结束。

第4步是明确的覆盖降级，不能宣称上下文完整。
它不推进摘要游标、不删除原文，也不允许丢弃安全必需条件后继续推荐。
API 合法输入本身也无法装下时，明确提示缩短/拆分，不静默截断。

建议初值如下，均待真实请求调参：

| 项目 | 初始建议 | 约束 |
| --- | --- | --- |
| 近期尾部 | 6个完整轮次 | token优先；未摘要尾部可能暂时更多 |
| 主触发 | 规则精简后预计输入占可用输入额度至少80% | 先判断可压缩性；当前调用前及回答后预测均检查 |
| 处理目标 | 本次评估基准下约60% | 有收益则处理；不能为达标删除必要信息或无限重试 |
| 辅助检查 | 超过8个未压缩完整轮次 | 重新计量及检查积压，不独立强制摘要 |
| 单批摘要 | 最多4轮 | 还受输入额度限制，不能拆坏确认事务 |
| 摘要投影 | 目标不超过1000个估算输入 tokens | 超额则重新压缩，不做字符串硬切 |
| 历史召回 | 最多3组，约1200个估算输入 tokens | 对象可辨认、片段完整 |
| 后台摘要 | 独立60秒、12000 tokens的任务总预算 | 输出、失败尝试和恢复均计费记账 |
| 维护并发 | 全局先限制为1个 | 低优先级，不占满聊天槽位 |
| 任务自动尝试 | 初始最多2次 | 失败保留待维护/失败状态，可在后续请求有界补救 |

后台独立预算只为了不挤占当前回答，不意味着免费或绕过全局费用约束；
记录到同一可观测性体系。重启不能清零已消耗额度，失败不能无限自动重排。
前台补压缩同时受维护任务剩余额度与当前聊天剩余额度限制，费用记录去重。
预算若尚不足以开始补压缩则不启动，直接走明确的覆盖降级。
是否降低总成本、是否改善延迟，均留待同批对话实测。

### 10.1 混合裁剪补充：按信息职责选择处理方式

2026-11-06 根据 xerina 指定的《AI Agent 通识教程》第5章
“5.4 混合裁剪：生产环境的实际方案”，直接读取站点HTML并核对相关示例。
来源为作者本人发布的章节：
[第5章上下文工程](https://ai-agent-guide.xiaofuge.cn/chapters/ch04b-context-engineering.html)。
以下是对本方案的设计补充，不是已实施能力或性能验收。

教程的核心思路是按消息类型/优先级组合保留、字段提取、摘要和省略，
而非对全部内容采用同一窗口或同一种摘要。本方案已经包含这些策略，
进一步明确选择规则和最终检查，避免只实现“6轮尾部+摘要”。

#### 信息保留规则

| 类别 | 本项目的内容 | 处理规则 |
| --- | --- | --- |
| 必须保留 | 系统规则、当前输入、有效安全条件、最新更正、真实待确认/写入状态 | 不作有损裁剪；过期条件先失效，不把所有历史约束永久固定 |
| 当前任务必要 | 当前对象和展示顺序、必要配方字段、营养口径、允许工具的参数与权限契约 | 保留完整语义和依赖，来源原文可用结构化引用表示 |
| 可压缩 | 旧完整对话、重复工具字段、已完成任务的过程说明 | 规则提取/去重优先，旧对话再作有界语义摘要 |
| 可从本轮投影省略 | 无关候选、重复资料、窗口外无新信息的寒暄 | 不注入当前输入；原始存储与摘要覆盖规则不变 |

分类依据内容的用途、来源、适用范围与依赖，不只看user/assistant角色、
句子长度或“闲聊”意图。近期完整尾部仍按第5节保留；
不能以“节约tokens”为由重新机械删除近期助手消息。
“不要了”“换一个”“就这个”可能撤销、替换或确认对象，不能当作无信息寒暄。
尤其不能丢弃确认/拒绝事件后让模型误判写入是否已经发生。

优先使用现有消息角色、意图、工具名、响应结构和任务状态完成分类，
在上下文投影上补类型、来源、有效期和依赖引用即可；
首期不增加一个每轮调用模型的“重要性分类Agent”。

#### 渐进式处理与提前触发

1. **每次装配均做规则精简。** 排除无关对象、去重、提取必要字段，
   工具定义沿用现有按意图白名单选择，不等模型输入爆满再处理。
2. **仍接近可用上限时压缩旧对话。** 保留近期原文和有效条件，
   对旧前缀执行第6节的摘要流程，优先后台维护。
3. **仍不足时有界补取或结束。** 只召回当前需要的原文，
   标明未覆盖范围；缺关键依据时澄清，不能靠删掉必要条件继续回答。

容量比例是主触发，轮数只用于尾部保留目标及辅助检查。每次调用前计算：

```text
本次可用输入额度 =
  min(
    当前模型窗口 - 本次输出预留 - 估算余量,
    整轮剩余额度 - 本次输出预留 - 后续必要调用预留 - 估算余量
  )
```

该额度内采用80%提前处理阈值和约60%处理目标作为本项目待验证初值，
避免一次轻微超额触发多次小摘要。最终输入上限是硬约束；
轮数和提前阈值均不能替代硬约束。初值来自本轮方案讨论，
不等于教程给出的固定实现或已验证最佳比例，完整调度规则见第10.2节。
必须在还留有摘要/下一次调用空间时介入，不能到预算归零才启动模型压缩。
摘要维护请求本身不再进入自动摘要触发入口，防止压缩请求递归触发压缩。

历史召回解决“需要早期细节”，混合裁剪解决“本次带什么、如何放得下”。
二者互补；召回结果也受相关性和额度控制，不能召回后又全部累积常驻。
后台摘要内容较旧，不会因此自动成为用户长期画像。

#### 保留依赖与最终检查

上下文选择按语义关联组处理：提问与对应回答、菜品展示与顺序、
工具调用参数与结果、写入预览与确认及真实执行结果。
本项目用JSON携带工具资料，保留必要调用/对象/状态引用即可，
不必为形式完整而重放所有历史工具协议消息。
事实投影仍须保留营养单位、整菜/每份、范围、可选配料及估算依据。

优先级用于决定取舍，不用于把全部历史按优先级重新排序。
最终组装仍保留各分区和分区内时间顺序，当前输入仅出现一次。
对最终序列化payload再次估算并检查：

- 必须保留内容是否齐全，普通短句是否承载更正或确认语义。
- 对象、来源、调用及操作状态的关联是否完整。
- 是否重复注入当前问题、旧摘要或同版本工具资料。
- 单次窗口、输出余量、整轮剩余额度和截止时间是否均满足。
- 原文覆盖是否连续；不连续时是否明确记录缺失范围。

工具schema只减少无关工具和经过审定的冗余描述，
不能用字符串切片破坏JSON、字段类型、必填项、枚举或权限/确认元数据。
本期不为压缩引入每轮动态改写schema的模型调用。

#### 原文使用边界

教程5.4的Python示例存在静态可见的问题：P4从未扣入的剩余额度再次扣减、
未先预留高优先级P1、返回时重复拼接P0，且没有最终总量硬校验；
其辅助摘要/提取函数也没有在该Python片段中给出完整实现。
TypeScript片段则对尚未计入的P4额度作加法，
并以字符串长度比例估算压缩结果，不能据此证明最终请求可容纳。
因此借鉴分类思路，不直接复制示例实现。

教程展示的压缩率不是本项目实测，也未用于确定本项目预算或性能承诺。
本轮没有核验其对Claude Code内部实现、固定阈值及其他框架行为的描述，
不把这些描述作为本项目必须遵循的规范。
原文中工具返回值预处理不保留大块原文的建议，
在本项目仅解释为“模型输入不携带原始大块内容”；
已有事实来源、执行追踪和必要原始依据继续按原存储策略保存。

### 10.2 比例触发的完整规则（最新整合）

#### 指标及基准

```text
W = 本次实际模型的上下文窗口
R = 本轮剩余token预算
O = 本次输出预留
F = 后续必要调用的保守预算预留
M = 单次输入估算余量

B = min(W - O - M, R - O - F - M)
I = 规则精简后最终序列化请求的估算输入tokens
u = I / B
```

`I`包括系统提示、输出结构、工具定义、当前问题、条件、画像、摘要、
近期原文、召回、相关工具资料以及结构校验反馈，不只计算聊天历史。
`F`覆盖本轮预期剩余必要调用的输入与输出；资料可能跨阶段重发，
不能只预留最后回答的输出。不为所有理论最坏分支无限预留，
按当前阶段、任务和已观察用量保守估算；工具计划变化时重新计算。
`B <= 0`时不计算比例、不启动新的模型压缩，直接走预算不足处理。
前台补压缩也要计入同轮成本；执行后重新计算`R`和`B`，
不能假定压缩省下的输入一定超过摘要调用本身的费用。

调用前用当前真实剩余额度；回答落库后的后台检查则用“下一轮预算预测”，
不能把本轮已经消耗到很低的`R`直接拿来决定下一轮一定需要压缩。
下一轮预测使用正常新一轮预算、保守的后续输入/资料增量；
预测不会作为实际调用许可，真实新请求仍重新检查。
备用模型、schema或工具集合改变后重新计算实际窗口和请求大小。

#### 状态与动作

| 规则精简后占用 | 决策 |
| --- | --- |
| `u < 0.80` | 正常执行；超过8轮仅记录/检查，不强制摘要 |
| `0.80 <= u <= 1.00` | 进入维护评估；有可压缩旧前缀则调度一次合并任务，目标约60%，当前调用满足硬约束时可继续 |
| `u > 1.00` | 当前payload不能直接调用；筛选资料、必要时有界补压缩，再重新计量 |
| 必需内容本身无法装下 | 不靠摘要反复尝试，澄清、拆分或有界结束 |

80%是维护触发信号，不是“到80%必须阻塞回答”的门禁。
后台新摘要默认供后续轮次使用；本轮必须使用时遵循第4节的版本增补规则。
只有达到触发条件且存在可压缩资料时才执行摘要模型；
若占用主要来自当前问题或必要工具事实，先缩小对象、分批读取或明确限制。

#### 处理目标及防抖

触发时记录`B_trigger`、请求/历史指纹、摘要版本、历史高水位和原因。
选压缩范围时以预计`I_after <= 0.60 * B_trigger`为目标，
至少处理一个可安全提交的连续语义组，同时受单批范围和维护预算限制。
不达到60%不等于压缩失败；必须保留内容、6轮尾部或维护上限限制收益时，
记录`target_unmet`和原因，最终是否能调用仍取决于最新硬约束。
如有后续后台批次，整项维护有总额度/次数上限，不能每批重置费用。

60%与80%之间留出增长空间；同一历史高水位、摘要版本、
模型/schema及资料指纹下合并触发，不在每个阶段重复排摘要任务。
无收益或失败后，按有界退避等待新数据、相关配置变化或明确重试；
同一已失败输入不能因高占用而无限重排，剩余额度下降也不是重试理由。
后来模型调用使`B`变小可能导致再次超80%，
此时先重算剩余任务是否可完成，不能无限通过摘要追逐不断缩小的分母。
任何最终请求都按最新`B`检查，不能使用旧的60%结论直接放行。

#### 执行时点

1. Worker开始新轮次，规则精简后首次装配时。
2. 每次意图、规划、回答或必要修订调用前。
3. 工具返回或历史召回增补后，进入下一次模型调用前。
4. 回答保存后，按下一轮预算预测做后台维护检查。

前台最多一次补压缩，不能在每个阶段各补一次。
摘要模型调用走独立维护入口，不触发自身；
同会话前后台共享维护归属，前台等待必须在既定短期限内并可取消，
不能无限等待后台任务。前台执行归属丢失时停止该前台任务；
后台维护只依赖维护任务归属，不借用已经结束的聊天run版本。

#### 算术示例与验收

假设某次可用输入额度`B=10000`，规则精简后`I=8200`，
则占用82%，进入维护评估，处理目标约6000。
另一种情况是装配初稿8200中有4000来自重复/无关工具资料，
先按规则移除，精简后4200只占42%，不必调用摘要模型。
规则精简后仍有8200且包含大量旧原文时，才选旧前缀压缩。
若成功后`I=6500`，但压缩消耗本轮预算导致最新`B=6000`，
这次仍超过硬限，不能按旧基准“已下降”就放行。
如果必要资料本身已有7000，则不能为达到6000删掉必要信息，
应记录目标未达到，并按最新硬约束判断是否可继续。

上述数字只用于说明算法，不是模型配置或真实开销。
必须测试79.9%/80%/100%/超过100%的边界、`B<=0`、
短对话大工具结果、长但低占用对话、无收益压缩、
分母下降、并发合并、连续失败、摘要任务递归及前后台费用去重。

## 11. 持久化与模块改动

### 11.1 最小数据设计

复用现有消息、任务、用户画像与反馈，新增两类会话维护数据：

| 数据 | 建议字段 |
| --- | --- |
| `chat_context_summaries` | `thread_id`、结构化摘要、`covered_through`、`version`、`history_epoch`、摘要schema/提示词版本、更新时间 |
| `chat_context_jobs` | 队列/会话、状态、待处理目标位置、预期摘要版本、执行版本、尝试次数、可重试时间、已用/预留tokens、截止时间、错误码 |

摘要表每会话一条当前版本；维护任务合并同会话的待处理目标，避免每条消息生成重复队列。
执行中的目标范围保持不变，新到需求记录为后续目标，不能篡改当前任务输入。
任务具有唯一活动约束和归属版本保护。
历史消息修改、来源失效和会话生命周期变化以 `history_epoch` 使旧任务失效。
建议在现有 `chat_threads` 增补 `history_epoch`、`effective_context`、
`effective_context_version`，作为历史失效和当前会话条件的权威状态；
摘要中的历史代号仅记录生成依据，checkpoint保存本轮使用的快照。
有效条件更新在消息/执行归属事务内校验版本并提交，
不能只保存在可能被旧运行覆盖的临时payload中。
画像的来源与版本随画像原子保存。
字段的最终 SQL 类型和 JSON 形状在实施迁移时固定，但上述一致性规则不留空。

新增明确的持久范围接口，例如 `latest_complete_turns`、`messages_between`、
`search_messages`、`load_context_summary`、`commit_context_summary`。
范围接口返回消息编号及稳定位置，不沿用只有 `limit/offset` 的分页作为摘要游标。
现有 `ConversationSummary` 是会话列表读模型，不能改造成历史语义摘要；
另用 `ConversationMemorySummary` 等明确名称避免调用方混淆。

## 12. Worker、失败与生命周期

摘要维护复用现有 Worker 进程，但用独立持久任务表，避免污染聊天API、
聊天完成消息和确认状态。沿用现有锁、执行版本和事务模式。
用户任务优先，维护任务只用有限空闲资源；摘要饥饿时记录积压，
下一轮按预算补压缩或明确覆盖降级，不能无限等待。

| 情况 | 处理 |
| --- | --- |
| 摘要模型超时/结构错误 | 不改摘要与游标；记录错误，按上限重试 |
| 保存失败 | 本次结果不算覆盖成功，恢复后重新校验提交 |
| 旧任务晚返回 | CAS/历史代号/归属检查拒绝覆盖新版本 |
| 回答提交后进程崩溃 | 已事务标记的维护任务重启后可领取 |
| 摘要提交后崩溃 | 任务完成与摘要同事务，重试不能再次推进 |
| 预算不足或持续压缩失败 | 保留原文，记录缺失范围，必要时澄清；不无限重试 |
| 会话入回收站 | 立即对召回与新上下文不可见，阻止维护提交并失效旧执行版本 |
| 会话恢复 | 保留历史与摘要；重新校验历史代号后恢复维护 |
| 七天到期清理 | 沿用checkpoint先清理及失败重试；再事务删除消息、摘要、任务、状态及引用 |
| 更正/删除画像 | 版本前进、旧来源失效；后台摘要无权恢复画像 |

清理要扩展现有顺序，不能新增外键后反而导致旧 `purge_thread` 永久失败。
正在运行的读取/发布提交要复核可用性，不能让已删除会话重新生成可见结果。
原始历史中的删除与回收站规则也适用于召回缓存和上下文缓存；
首期尽量不增加独立缓存，避免多套失效机制。
应用追踪不额外复制整份个人历史；摘要及来源清理纳入相应保留策略。
数据库备份的保留期属于现有运维策略，不能宣称在线清理会同步抹除历史备份。

## 13. 可观测性

每轮记录来源清单和分区统计，便于确认“模型实际看到了什么”：

- 基础上下文/增补版本、历史高水位、摘要版本及覆盖位置。
- 近期原文的消息编号、范围和轮次，召回片段来源。
- 画像和有效条件版本、本轮工具对象及版本。
- 各分区估算输入tokens、总实际usage、模型/提示词版本和调用次数。
- 可用输入额度、占用比例、后续调用预留、触发基准与处理后最新比例、
  目标是否达到以及未达标/未启动压缩原因。
- 压缩触发原因、延迟、失败码、重试、CAS冲突与维护积压。
- `coverage_complete`、未覆盖位置范围及取舍原因。

这些字段主要用于Trace和验收记录，聊天正文不展示内部术语。
现有降级机制若需要用户知道缺信息，用简洁自然语言表达。
“有来源编号”不等于语义正确，“发布成功”不等于记忆正确。

## 14. 迁移、灰度与回退

1. 先加表、字段、接口和测试，保持旧读路径可运行。
2. 历史消息沿用原位置和ID，不重编号；现有截断摘要无可靠覆盖信息，
   不能导入为已覆盖全文的正式摘要。
3. 对有持久原文的旧会话，从游标0开始分批生成摘要；
   首次访问可有界补建。原文实际缺失时记录缺口，不能从checkpoint补造历史。
4. 先离线比较新旧上下文清单，再用隔离测试用户运行真实多轮，
   确认结果、预算和恢复后再切换主读取路径。
5. 摘要回填低优先级，不能启动全量无上限模型调用。
6. 用一个重构读路径开关进行灰度/回退；具体配额配置保留少量必要项，
   不为每个意图建立独立窗口参数。
7. 回退停用新维护与新读取，不删除原始消息或已新增数据；
   删除和权限限制继续生效。新保存画像字段仍需兼容读取，
   不能直接退到会拒绝这些字段的旧二进制版本。

切换前核对记录数量、内容哈希、用户归属和待确认操作。
新旧上下文在正式执行中只选一份，不让影子分析重复执行写入工具。
若改了有效条件的数据形状，提供旧checkpoint兼容读取，
执行中途不混用新旧版本；必要时先让活动请求结束再切换。

## 15. 分阶段实施与验收

### 阶段A：统一上下文和会话记忆闭环

范围：持久范围读取、完整近期对话、有效条件撤销、滚动摘要、
独立预算、持久维护任务、失败恢复和删除联动。
这些能力可以拆提交，但不能在缺少覆盖/失败恢复的情况下宣称长对话记忆完成。
先验证闭环，再接下两个阶段；不顺带改正文质量门禁。

### 阶段B：有界历史召回

范围：按对象、关键词、日期读取原文，当前会话优先，
显式跨本人会话查询、来源引用与无结果澄清。

### 阶段C：长期画像增强

范围：来源与版本、显式聊天保存、现有画像查看/修改/删除、
厨具等确有需求的字段及旧来源失效。
安全必需的画像读取和更正保护从阶段A就保留，
不能等到阶段C才处理已知过敏条件。

### 工程验收

- 单元：轮次归组、来源校验、窗口选择、连续覆盖、预算、
  条件set/add/remove/clear、作用域/日期失效及版本冲突。
- 混合裁剪：短句更正/确认不被误删、必要工具契约完整、
  关联组与时间顺序保留、当前输入只出现一次；
  处理后最终payload重新计量，超额不得继续发布，维护不能递归触发自身。
- 比例调度：80%软触发、60%目标、100%硬限及边界；
  新一轮预测预算与当前剩余额度分开，分母下降不引起无限压缩，
  低占用长对话不因超过8轮强制摘要。
- 集成：三阶段payload承接一致、工具证据独立、持久化、
  前台补压缩不绕预算、摘要任务低优先级、跨用户隔离和回收站。
- 进程恢复：回答落库/摘要提交前后强制终止，重启验证无漏任务、
  无重复消息、无重复写入、游标不倒退且费用不重置。
- 数据库：SQLite和实际PostgreSQL事务/并发测试，
  迁移升级和旧数据导入；内存通过不能替代PostgreSQL验收。
- 运行项目要求的相关Ruff、mypy、pytest；
  触及前端时运行typecheck/build及画像交互验证。

### 真实多轮验收

建议至少8组独立会话，每组不少于20轮，确保跨过多次摘要边界。
另用定向故障测试覆盖不能可靠靠自然对话触发的场景。
数量是验收起点，不能自动推出整体准确率。

| 场景 | 必须观察的结果 |
| --- | --- |
| 推荐后问“第二道”“刚才为什么选它” | 对象与展示顺序正确，助手历史可用于理解 |
| 切到通用问题再回到原菜 | 对话承接保留，无关菜谱移出，回问时补取事实 |
| 早期人数、日期、禁忌跨多次摘要 | 有效条件保持且来源可查 |
| “今天不辣”与“以后不辣” | 临时/长期范围正确，跨日不误用 |
| 取消热量上限、移除食材限制 | 条件真正撤销，旧摘要不复活 |
| 画像过敏与当前说法冲突 | 不静默解除限制，不把食品过敏原当用户过敏 |
| 重复工具、大配方、长助手回复 | 工具不持续挤掉对话，超额如实标记 |
| 召回早期具体数值/历史原话 | 原文可追溯，历史说法与当前验证事实分开 |
| 压缩失败、重试、并发和进程重启 | 游标/版本正确，原文未丢，任务与费用有界 |
| 用户隔离、删除、恢复及到期清理 | 无越权召回、旧任务提交或删除信息复活 |

验收同时看真实输入清单、来源、人工记忆判断、现有事实安全回归、
累计tokens、费用、调用次数和延迟。确定性覆盖/权限不变量必须全部通过；
真实模型仍有摘要遗漏或引用错误时保留反例、修复后重验，
不能用调用成功率、发布率或Fake测试结果替代。
性能用相同问题序列对照，分别报告前台耗时和后台维护费用，
不在实测前承诺6轮完整原文一定能满足现有预算。

## 16. 本轮交付与未完成事项

已完成：现有实现核对和完整设计文档，更新设计入口及项目状态。
未完成：业务实现、SQL迁移、配置生效、模型窗口核对、工程测试、
真实多轮验收、性能/费用测量和生产切换。
本方案不能保证无限上下文、摘要无损、关键词召回全命中或消除模型幻觉。
下一步建议先评审总体边界及参数初值，再实施阶段A。
