## 工程原因与处理方向

1. **任务边界没有收敛。** `recommendation.py:49` 的共享提示词允许通用烹饪
   与改进建议，又包含高蛋白搭配等内容；做法子任务虽要求原文整理，
   数值门禁却要求所有具体数值有依据。模型在“详细做法”中继续补常见包装克重、
   保存或冷藏时间，未遵守具体子任务。优先按意图明确生成职责，
   而不是继续在共享长提示词末尾堆禁止项。
2. **修订实际变成重新生成。** `recommendation.py:314` 遇到纯数值问题就
   `pop("message")`，反馈要求局部修订，但模型看不到待修改句子。
   本例的成对实验支持优先保留待修稿，按明确错误修订，再走原有安全校验。
3. **历史已发布内容不是可靠事实。** 上一轮“皮蛋豆腐怎么做”的已发布稿加入
   原文没有的南豆腐、蒸鱼豉油、蒜末、榨菜末等内容，又进入本轮近期消息。
   原提示词去掉这些消息仍失败，说明它不是本例必要触发条件；
   也不能因此把历史助手正文升级为事实依据。
4. **数值门禁只说明是否有依据。** `answers.py:810` 检查数值/单位是否在证据中，
   不证明语义归属、全部步骤正确或未写数字的内容安全。
   本次数字确实不在允许依据中，未发现截断、单位解析或来源丢失导致的误拦证据。
   不应靠取消门禁或直接把缺失数字补进种子库解决。
5. **可观测性不足。** 原失败稿未保存，现有记录只能解释被拒数字和降级路径。
   后续如增加失败稿诊断，应采用有界保存、身份隔离与敏感信息处理，
   不能把全量对话无条件写入日志。

另一个已观察到的限制：本轮生成状态的 `dietary_constraints.allergens` 为空，
当前与历史证据只有菜谱，用户过敏信息仅在历史助手文本里出现；
原降级稿仍逐字展示“花生碎（可选）”。当前请求未独立带入可验证用户画像，
这不是本次数值降级的原因，但收窄提示词不能解决该安全上下文缺口。
“移除助手历史”是诊断变量，不是可直接上线的安全方案。

## CookHero 意图与提示词补充核查

2026-11-05 按 xerina 要求，通过 GitHub 官方 API 和原始文件重新核对
`Decade-qiu/CookHero@ca2f79a3200ee75cd6ff560f354b29d025d87aa0`。
此次 API 查询的 `main` 树 SHA 与该快照相同；只读源码，没有运行 CookHero。

- 普通对话的 `app/conversation/intent.py` 定义菜谱、技巧、食材、闲聊和推荐五类，
  独立的意图识别提示词用于输出 `need_rag`、`intent` 和判断理由。
- `app/services/conversation_service.py` 的 `chat` 根据 `need_rag` 准备检索上下文；
  最终统一调用 `_generate_response`。该函数结合检索、搜索、历史和用户资料构建消息，
  没有根据上述五种意图选择五套最终回答提示词。
- 普通对话统一使用 `app/conversation/prompts.py` 的 `SYSTEM_PROMPT`；
  同一提示词覆盖做法、技巧、推荐等任务，允许检索不足时补充通用安全常识。
- Agent 是另一条链路。`app/agent/__init__.py` 将默认 Agent 注册为
  `DEFAULT_AGENT_SYSTEM_PROMPT`；其定义在 `app/agent/prompts/default.py`，
  是通用饮食与烹饪提示词。`DefaultAgent` 没有额外意图分支，
  `BaseAgent` 通过同一工具循环回交工具结果、生成回答。
- 专业子 Agent 存在独立提示词，例如
  `app/agent/subagents/builtin/diet_planner.py` 的
  `DIET_PLANNER_SYSTEM_PROMPT`。这是按专业角色分工，
  不能等同于每个普通问答意图都切换一套提示词。

因此，做法专用提示词是本项目对照实验支持的一种修复方案，
不是 CookHero 的默认实现。“共用提示词”本身不足以判定架构有错；
本项目需要处理的是生成允许补充内容与具体菜谱数值门禁之间的契约不一致，
以及修订删除原稿的问题。也可以保留共享提示词、补清意图适用边界后再真实验证，
本轮未替该方案运行新的模型对照，未据源码宣称 CookHero 不会补数或整体效果更好。

再次针对“共享主提示词 + 短任务说明”核对同一固定提交：
`app/services/conversation_service.py:609–639` 的 `_generate_response`
只传入合并资料、用户资料与历史；`app/context/manager.py:51–111`
的 `build_llm_messages` 组装共享提示词、个性化信息、历史和额外资料，
没有根据普通对话的五类意图追加不同回答任务指令。
`_build_combined_context_prompt` 追加的是视觉、检索、搜索等资料说明，
不能与NutriPilot按意图选择的短任务指令混同。
因此只能说共享提示词这一点相同；保留短任务说明是本项目现有结构的工程选择。
