# 回答证据、计算与重试修复

日期：2026-11-04。最终源码：`intent-v14`、`planner-v16`、`recommendation-v42`。

## 目标及边界

延续 Agent 自主选择菜品、组织正文的方向，程序提供可靠事实和计算，并守住发布边界。
正常回答不改用固定模板，不增加依赖、服务或总调用预算；继续保留原有一次正文修订、
过敏校验、医疗安全、身份隔离、写入确认、幂等和执行归属校验。

本轮没有重新检出或对照 CookHero，不以架构方向相似宣称达到同等回答质量。
已有回收站、页面布局及此前未提交改动均保留。

## 已实现

- 补齐当前候选的比较资料，历史候选按实际展示或本轮指代保留，避免依据缺失造成
  “唯一”“最好”等断言无法核对。历史助手正文仍不作为事实证据。
- 将规范化卡片注册为 `verified_facts` 引用记录，只证明对象和状态，不包含兜底正文。
- 程序计算每100千卡蛋白量、相对蛋白差值，以及Agent声明的候选营养差值和百分比。
  原始区间有不确定性时不生成伪精确换算；每100克换算必须有成品重量依据，
  不把原料投入量当成品重量，也不据此推断人数或个人适用性。
- 审核增加数量提取是否存在、全文一致性两个明确字段，程序核对模型提取的对象及数量。
  仍由模型理解单复数语义，不引入数量关键词拦截规则。
- 拟通过的审核必须覆盖每个正文句子与非空推荐理由；证据编号、字段路径及值必须真实。
  紧凑JSON可引用真实字段子集，逐项核对源对象，未知字段、错值、错对象仍拒绝。
  来源条件可引用正文相邻句，避免条件在下一句时误拒。
- 未通过的审核直接进入原有修订，保留引用错误反馈；不为修复否决报告的引用另耗模型调用。
  否决结果不能因跳过引用格式重试而获准发布。
- 工具白名单与未知顶层参数在现有网关结构化重试中给出准确反馈；
  原 Planner 和工具执行边界的完整类型、安全校验继续保留。
- 缩减重复提示词，网关按实际用量校准保守预算估计，并使用紧凑JSON。
  按完整句子审核，生成最多2048输出Token，审核保留最多4096输出Token。
  不再因审核说明超过240字而判结构失效，整轮仍为90秒、24000 Token。

## 实测中撤回的尝试

提前为审核预留过多预算导致有候选但连生成也未执行；按逗号、冒号切分短句割裂条件
和结论，并放大审核输出；过低的审核输出配额导致JSON被截断。这些尝试已撤回，
失败报告保留，不能作为最终质量通过的依据。

## 验收口径

固定20例包含正确食材匹配、无依据排名/功效/做法、遗漏来源成熟条件、单复数、
全体与子集对象、一般补救、前后矛盾、混合真假断言。既检查程序拒绝，也单独记录
模型语义判断；格式误拒不能算语义判断正确。

完整对话覆盖高蛋白午餐、脂肪较少的替换、食材推荐、指代原因、配方、
通用原理及补救、寒暄、未知指代、空检索、比较与再次追问。
第一轮无卡片时不会执行依赖它的换菜，因此可能少于14轮，应如实记录。

“审核正文已发布”仅为流程指标，不代表事实正确、自然表达合格或整体质量准确率。
需要人工检查已发布正文是否包含来源未支持的优势、个人份量误用或危险推断。

## 剩余原因与优先级

1. 生成仍会从菜名、食材延伸到做法、口感、份量及适用性；资料补齐不能保证模型遵循。
2. 审核可能只确认句中部分真实事实，忽略同句的无依据说法，或误解来源中的必要条件。
3. 单轮证据、逐句审核及结构修复仍然消耗大量Token。保留一次修订时，24000总预算
   可能不足；单纯放大输出、添加提示词或提高发布率均不能视为解决。
4. 空检索的事实兜底本身有用，但严格验收仍将未发布审核正文记失败。
   应区分可靠空结果、误拒和实质错误，本轮未为了通过而放宽验收门槛。

下一步应针对发布漏判和实际降级调用记录重新收敛审核契约与证据投影，并单独验收
来源完成条件、整菜/一餐口径。不能继续仅靠叠加具体反例提示词宣布质量提升。

报告的调用量与Token来自执行事件。若调用在预算耗尽异常时未归集用量，汇总会少于实际
提供商计费用量，因此不把这些事件统计宣称为完整成本账单。
