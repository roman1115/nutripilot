# 100 道菜谱的日常推荐链路验收

验收日期：2026-10-29（Asia/Shanghai）。

## 范围与结论

本轮验证现有 100 道计算配方在日常推荐、营养查询、约束过滤及多轮换菜中的使用。继续按整道菜计算和展示，不新增人数整理、人均计算或个人份量推断，不把单道菜标为完整一餐。原有 18 道演示餐食保持兼容，完整餐单仍依赖这些记录。

离线回归、真实 BGE 检索和浏览器检查通过。真实 Qwen 请求受到提供方额度限制，不能报告 Qwen 验收通过。所有小样本结果只对应本轮固定场景，不是整体推荐准确率。

## 发现及修复

1. 对全部 100 道菜使用完整菜名进行 Hashing/Lexical 检索，修复前有两条首位不匹配：“米粥”被“小米粥”抢先，“清蒸鲈鱼”被“清蒸鲈鱼配时蔬”抢先。现在先执行安全和结构化过滤，再在召回截断、融合截断及最终排序中保留精确菜名或别名优先；其余候选沿用混合排序。检索版本为 `hybrid-rrf-v3`。
2. “推荐一道清淡的菜”原来会追问早餐／午餐／晚餐。现在对明确的一道菜、几道菜或菜谱请求允许不限定餐次；普通“给我推荐点吃的”仍保留澄清。Prompt 更新为 `intent-v4`，尚未经本轮真实 Qwen 验收。
3. 上一轮候选在新一轮读取画像等工具后会被当前空候选覆盖，单靠模型提供排除参数无法保证换菜。现在保存上一轮候选快照，调整意图下由工具执行边界强制合并排除。测试模拟模型重复使用同一检索词并删除排除参数，仍无法重新推荐上一批候选。
4. Fake 模式原来没有提取准备时间限制，导致“10 分钟内做好”未落实筛选。现在支持“10 分钟内／以内”和“不超过／控制在 10 分钟”等形式，沿用已有槽位与强制约束注入。
5. 预算和准备时间未知的配方原本已被过滤，本轮保留该行为，并在回答中说明未知数据未纳入候选。当前所有新配方的价格、准备时间均未知；“10 分钟内的午餐”没有符合条件且时间已知的候选，正确返回无结果。
6. 首页清淡晚餐示例改为“晚餐推荐一道清淡的菜”，移除原示例隐含的 40 元预算，避免默认排除全部价格未知的新菜。

没有补造价格、烹饪时间或口味标签。“清淡”等软偏好下，原有餐食可能因已有标签排在新菜前面；不保证每次推荐都出现新菜，也不把模型推断当成数据事实。

## 验证结果

### 自动化与离线回归

- 后端：`pytest` **218 项通过**，1 条既有依赖警告。
- Ruff 通过；mypy **95 个源文件通过**，含现有导入和草稿脚本；前端 typecheck/build 通过。
- 实际 100 道菜名逐一检索，首条 ID 全部匹配；同时核对整配方口径、投料重量标记、计算估算状态及来源。另用偏向其他菜的检索索引和重排器，验证精确命中不会被截断或错误排序挤掉。
- 定向测试覆盖新菜推荐、模糊食材描述、整菜六项营养区间、来源、换菜、过敏过滤、价格／时间未知以及无法满足热量上限时不虚构小份量。
- Fake + Hashing/Lexical：核心 **60/60**、既有扩展 **8/8**、新增推荐场景 **14/14**。
- 新增固定数据集：`evals/datasets/catalog-recommendations.json`。包括无餐次点菜、指定菜名、食材描述、热量／预算／时间条件、过敏、无候选、多轮换菜、营养范围及未知菜名。
- 报告位于 `.runtime/catalog-use-evals/`。Fake 报告中的 Token 是演示估算，不是实际模型用量或账单。

### 真实 BGE

使用现有本地 BGE-M3 和 BGE Reranker v2-M3，CPU、4 个计算线程、离线模型文件、内存数据与向量索引；没有连接 Qdrant。

- 直接检索 **8/8**：米粥、清蒸鲈鱼、红烧鲤鱼、番茄鸡蛋食材描述、鸡蛋过敏、整菜热量上限、未知价格排除、未知准备时间排除。
- “番茄和鸡蛋做的菜”前三条包括新配方“西红柿炒鸡蛋”和“西红柿鸡蛋汤”。
- 热量上限 400 千卡的午餐检索返回新配方，全部按整菜热量上限检查。
- 单独进程首次检索含模型加载约 22.09 秒，其他有候选的普通检索约 2.78～5.99 秒；只有一条已知价格候选时约 0.15 秒，无时间候选时不执行推理。均为本轮单次观测，不是性能基准。
- 另通过应用容器及进程内 MCP，以 **Fake 对话模型 + 真实 BGE** 跑新增 **14/14**。单次整套场景平均约 3.16 秒、P95 约 10.35 秒；不能当成 Qwen 对话延迟。
- 原始报告：`.runtime/catalog-use-bge.json`、`.runtime/catalog-use-evals/catalog-bge-fake.json`。

### 浏览器

实际使用本地 Chrome：

- 既有完整浏览器回归通过：推荐、Trace、营养别名、多轮历史恢复、历史切换、餐单确认与保存。
- 首页图片与布局在 1440、1024、768、390、320 像素宽度下检查通过。
- 对新增配方另验桌面 **1440×1000** 和手机 **390×844**：实际提交“午餐推荐红烧鲤鱼”，卡片显示 **1741.6～1962.6 千卡**，保留整道菜、投料重量及来源。
- 页面刷新后可恢复推荐；继续发送“换一批”，显示的菜品与上一批不重复。无横向溢出或 JavaScript 错误。
- 截图和结果：`.runtime/catalog-use-browser/`，其中 `catalog-1440.png`、`catalog-390.png` 和 `catalog-result.json` 为新增配方定向证据。

## 真实 Qwen 阻塞与重跑

本轮实际启动了配置为 `openai` / `qwen-plus` / BGE 的本地 API，存储为内存、MCP 为进程内模式。一次对话的 Intent 调用发生 `MODEL_REQUEST_REJECTED` 并降级；不能把该响应算作真实模型成功。

随后直接请求提供方，确认返回 **HTTP 403 / `AllocationQuota.FreeTierOnly`**；2026-10-29 11:38（Asia/Shanghai）再次检查仍相同。说明当前调用受到提供方免费额度／计费配置限制，不能据此推断为网络失败或代码输出错误。本轮没有更改账号计费、模型配置或凭证，也没有切换到未配置的其他模型。

仅保留不含凭证的结果：`.runtime/catalog-use-qwen-blocked.json`。首次应用 Trace 保存在 `.runtime/catalog-use-real.sqlite3`。

提供方恢复可用且真实 API/BGE 启动后，复用现有严格验收脚本：

```bash
.venv/bin/python scripts/verify_real_regressions.py \
  --base-url http://127.0.0.1:8001 \
  --dataset evals/datasets/catalog-recommendations.json \
  --timeout 1200 \
  --output .runtime/catalog-use-qwen-bge.json
```

该命令会实际调用模型，使用数据集中的专用测试用户 `910029`。必须检查真实调用、非降级证据及失败用例，不能仅根据报告通过比例声称真实 Qwen 效果。
