# 本轮需求与推荐理由验收

验收日期：2026-10-30。

## 原因与改动

真实会话中，用户说“想吃鸡胸肉”，系统曾返回凉拌鸡丝、汤面、烤鸡翅，
而理由统一为“符合你的菜系偏好：中式”。相似度检索没有强制包含鸡胸肉；
推荐生成未接收本轮用户原话，最终事实归一化又把理由替换成了画像偏好。

本轮调整：

- `required_ingredients` 从意图槽位贯穿规划、工具执行边界、MCP 参数和检索过滤。
  每项必含食材均须在实际食材记录中匹配，先过滤再排序；过敏与忌口继续优先执行。
  工具边界补齐参数，规划模型遗漏该字段也不能放宽要求。
- 本轮明确食材替换旧要求；单纯“换一批”继承原要求。
  新推荐或新餐单不自动沿用上一轮必含食材，否定、过敏声明不转成必含项。
- 推荐 Worker 接收 `user_message`，先依据本轮需求选菜。
  最终理由由原始食材、营养保守边界及实际限制生成，先解释与本轮问题的关系，
  再按需补充画像；有明确食材时不再重复菜系画像。
- 明确食材的候选不足三道时允许少推荐，没有符合要求的配方就如实说明。
  最终归一化再次检查必含食材，模型选错候选时仅使用已检索到的合格菜品。
- 做法查询、来源引用、整菜营养范围、用户过敏与食物过敏原的区分保持原有边界。
  没有增加 Worker、依赖、个人份量算法或修改来源数据。

解释仍采用有依据的确定性表达，模型负责理解需求和选择候选；
没有直接放开任意模型理由，避免把未经验证的营养、耗时、价格或个人健康事实展示出来。

## 实际验证

最终代码运行：

```text
NUTRIPILOT_TEST_EXTERNAL=1 .venv/bin/pytest -x

```

包含真实 PostgreSQL/Redis/Qdrant、认证 HTTP MCP 参数往返，以及以下新增场景：

- 鸡胸肉必含过滤、多项食材全部满足、无匹配不放宽、与过敏冲突不放宽。
- 做法查询后“想吃鸡胸肉”，不沿用旧菜名，也不因规划漏参改推鸡翅。
- 换一批继承食材、新食材替换、否定不变必含、新餐单清除旧食材。
- 理由中食材和本轮限制优先，画像在后；未知准备时间不能生成快捷理由。
- 模型编造的个人健康事实、错误候选与营养数值继续被拦截。

Ruff 全仓通过；mypy 应用及浏览器脚本 100 个源文件通过；
前端 `npm run build`（含 TypeScript 检查）通过。

已重载本地 5178 真实入口和 5177 Fake 持久化入口。
两者通过实际浏览器连续六轮：

1. 推荐午餐。
2. 这个怎么做（多个候选时澄清）。
3. 第二道怎么做。
4. 给我西葫芦炒鸡蛋的做法。

> 凉拌鸡丝的这份配方用到了鸡胸肉，符合你这次想吃的食材；整道菜热量不超过你设定的 600 千卡。

Fake 入口同样通过六轮，但不计入真实模型效果。
桌面 1440×1000、390×844 和 320×740 手机、刷新恢复均通过；
无页面横向溢出或 JavaScript 错误，已查看实际截图。

## 限制

- 必含食材目前按标准食材名称包含关系匹配，没有新增通用同义词解析器；
  未匹配时可能没有候选，不能据此推断配方库完全没有该类食物。
- 未知价格、耗时和未标注口味不编造；汤面等可选做法只解释本项目收录版本，
  不宣称所有同名菜都使用鸡胸肉。
- 这是固定场景的功能验收，未重跑全套真实模型效果数据集，不能外推整体准确率。
- 既有历史回答保留原文；未执行完整应用镜像构建、公开部署或生产负载验收。
