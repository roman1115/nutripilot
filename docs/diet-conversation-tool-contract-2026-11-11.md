> 本文件现为设计过程记录，C01–C24保留为验收场景。
> 后续实施以[饮食管理实施基线](diet-management-implementation-spec-2026-11-11.md)及其
> [严格工具Schema](specs/diet-management.schema.json)为准；尤其计划create使用entries批量参数。

日期：2026-11-11。状态：完整方案的契约补充，尚未实现。
上位方案：[饮食管理完整交付方案](diet-management-complete-design-2026-11-11.md)。
本文件明确“会话自动填写、按问题查数据、预览确认”如何接通；全部属于同一完整交付范围。

## 1. 入口与职责

用户消息 → 意图与事件拆分 → 字段提取及来源校验 → 资料匹配/定向查询 →
程序计算 → 可编辑草稿或回答 → 显式确认 → 同一应用服务事务提交。

只读查询不弹写入确认；生成草稿允许持久保存草稿，但不进入实际摄入统计。
模型不能提交SQL、指定数据表、决定用户身份、直接批准操作或写入最终营养合计。
手动表单、聊天、文字解析、图片解析和计划转记录共用数据模型、校验及提交服务。

## 2. 会话意图与事件

| 输入含义 | 处理 | 不得产生的副作用 |
| --- | --- | --- |
| “这周蛋白质吃得怎么样” | 查询有效记录汇总、当期目标与完整度 | 不创建记录，不修改目标 |
| “今天午餐吃了……” | 提取本人实际食用事件，形成草稿 | 不跳过核对直接入账 |
| “帮我记下今天午餐……” | 结合明确的已食用事实建草稿；仅安排午餐时归计划 | 不仅因“记”字推断已吃 |
| “明天打算吃……” | 计划草稿/变更预览 | 不计入实际 |
| “如果吃两碗会怎样” | 假设计算，结果标假设 | 不形成真实食用事件 |
| “番茄炒蛋怎么做” | 沿用做法问答 | 不记成已吃 |
| “我朋友午餐吃了……” | 普通知识讨论或澄清主体 | 不写入本人记录 |
| “其实没吃那道菜” | 未确认时移除草稿项；已入账时定位记录并生成更正/删除预览 | 不生成负份量或新食用记录 |
| “以后每天目标改成……” | 目标变更预览，明确生效日 | 不改当日实际，不默改过去目标 |
| “不喜欢这道菜” | 沿用偏好/反馈机制 | 不删除实际记录 |

一条消息可以包含多个事件：“昨天吃了米饭，明天想吃面”分别形成实际与计划草稿，
不共用日期或互相污染。多事件预览分别可选，不以一次含糊确认批准全部事件。
时态、否定、主体或所指记录无法确定时先澄清，不靠单个关键词或模型置信度直接写入。

## 3. 字段来源与自动填写

### 3.1 字段证据

每个提取字段保存`value/original_text/source_kind/source_ref/operation/status`：

- `source_kind`为`user_message/user_form/active_draft/catalog/label/model_estimate/server_default`。
- 消息来源包含稳定message_id和原文片段；服务端检查片段存在，单位与日期归一化另行验证。
- `operation`仅`set/clear/keep`，不以缺字段推断清空；字段取消与数值0严格分开。
- `status`区分`explicit/derived/proposed/unresolved`；推导说明必须保留，不能把建议冒充用户原话。
- 人工表单更正及最新用户明确更正优先于先前提取，保留修订来源；
  资料匹配事实只能提供食物依据，不能覆盖用户说自己吃了多少。

消息片段只证明“说过这些字”，不能单独证明语义、主体、时态或数量归属正确；
固定语义用例、草稿展示及最终确认共同覆盖这些问题。
每个食物条目有稳定item_id，数量、单位、生熟状态与证据必须绑定该条目，
不能把“米饭150克”的数量分配给同句另一道菜。

### 3.2 自动填写规则

| 字段 | 自动填写依据 | 缺失或冲突时 |
| --- | --- | --- |
| 本人身份 | 服务端认证上下文 | 无有效身份拒绝访问，不接受模型生成user_id |
| “今天/昨天/本周”等 | 提交消息时刻、该次IANA时区、相对时间表达 | 后端解析并在预览展示绝对日期；矛盾日期先追问 |
| 未提及日期 | 草稿建议消息提交当地日期，标为默认 | 必须在确认卡可见；不能声称用户已明确日期 |
| 餐次 | 用户明确早餐/午餐/晚餐/加餐 | 不按当前钟点猜，提交前选择；“宵夜”可规范为加餐并保留原词 |
| 食物与主体 | 本轮原话、选中表单或已明确的活动草稿 | 多候选展示选择；第三方主体不进入本人记录 |
| 数量与单位 | 用户原话或标签识别后人工核对 | 可追问、手填或明确保留未知，不默认一份 |
| 生熟/可食部 | 用户明确、所选食品资料及适用状态 | 不拿生重套熟重；匹配不明则澄清或保留营养未知 |
| “同上一餐/再吃一次” | 已定位的本人实际记录/计划及用户明确复用范围 | 展示复制内容并新建事件草稿，不直接复制入账 |
| 备注 | 本轮明确补充或人工输入 | 不将推测性健康结论写成用户事实 |
| 营养和换算 | 版本化目录、标签、用户资料或标明的模型估算 | 程序计算；找不到依据保留未知，确认不升级为已验证 |
| 目标与长期偏好 | 明确更新请求并经各自确认机制 | 实际食用、短期要求不自动更新画像或目标 |

相对日期以消息提交时刻为锚点，排队、Worker恢复、午夜过后续跑都不能重新解释。
查询未指定范围时默认只查询提交当地日期，答复明确范围；“这周”等按已声明周起始日计算。
来源标识、资料版本、record_id和确认令牌来自服务端，模型不能自行创造并使其有效。

### 3.3 澄清与未知值

提交实际记录必须明确本人、实际食用语义、当地日期、餐次以及至少一个可识别名称的条目。
具体食物数据库匹配、份量和营养允许未知；因此允许“外卖炒饭，份量不详”如实保存。
预览用待补字段区分：

- `blocking_fields`：主体/实际或计划类型不明、无食物名称、日期冲突、无餐次等，需解决后提交。
- `optional_unknowns`：未匹配食物、未测重量、无法换算“一碗”等，提示影响并允许用户保留未知。

系统优先合并本次必要追问，已明确字段不反复询问。
用户说“不清楚，按未知记”只解除允许未知的字段，不能绕过主体、权限或日期冲突。
输入“半盘”会保留“半盘”的数量描述；它不等于整道参考菜谱的二分之一。

## 4. 多轮编辑与确认生命周期

### 4.1 识别活动对象

草稿和变更预览绑定`user_id/thread_id/source_turn_id`，有独立ID、版本及24小时绝对有效期。
新建实际记录使用`intake_drafts`作为草稿和预览的唯一数据源；
更正记录、计划和目标使用`diet_change_previews`保存有类型操作、对象版本、内容哈希、
有效期、状态与提交回执引用。两者共用预览契约，不在聊天检查点再维护一份可写正文。
同一会话可有多个草稿，但只有用户已选定或唯一明确所指的草稿作为活动对象。
跨会话“继续刚才那个”先查本人候选并选择，不把全部会话草稿直接拼入上下文。
应用编排器按身份加载活动草稿的有界投影，模型无需额外获得任意草稿查询工具。
数据权威在数据库；LangGraph只保存草稿引用和版本，恢复时重新核对有效状态。

### 4.2 补充、更正和话题切换

“米饭是熟重”“把150改成100”“那份不要了”等生成面向具体item_id的字段补丁。
一个草稿有多份米饭或多个数值时先定位，不修改所有同名条目。
已有草稿的日期、数量可以承接；普通新记餐不继承上一顿的食物、份量或餐次。
闲聊和问做法不清空未确认草稿，也不自动将其确认；回到记餐时先读当前版本。
模型重新解析不覆盖用户人工锁定的字段；解除锁定须用户明确选择重新识别。
草稿修改后原预览哈希失效，旧确认按钮即使仍在另一标签页也返回409。

### 4.3 确认与提交

预览至少显示实际/计划/目标操作、绝对日期与餐次、食物条目和数量、
未知项、估算说明、来源、操作范围及受影响记录。
展示的是应用服务验证后的草稿，不能仅用模型自由文本充当最终预览。
用户操作按钮或明确“确认保存”触发后端确认入口，绑定唯一当前预览；
“好”“知道了”“继续”本身不构成写入授权。多个预览或已过期时要求明确选择。
自然语言确认由服务端当前待确认对象解析，不能信任模型输出的`approved=true`。
未通过校验的草稿不能通过聊天里的“直接保存”绕过。

确认校验用户、对象归属、草稿/目标版本、内容哈希、有效期、权限、计算版本与幂等键。
正式提交时重新验证所引用的实际记录或计划版本；
目录新版本不自动替换预览已有资料快照，资料被撤回/禁用则返回重新核对。
不能改变预览内容后沿用旧批准。成功后回执返回记录ID、版本和营养完整度，
聊天与饮食页面读取同一结果。数据库尚未确定提交成功时答复“处理中”，不提前说已保存。
重复确认返回原记录，取消确认仅放弃待处理操作；已入账数据需另走更正/删除预览。

### 4.4 单个例子

固定测试时钟为2026-11-11，用户说“今天午餐吃了150克米饭和半盘番茄炒蛋”：

1. 自动填写2026-11-11、午餐，两条食物分别保留“150克”和“半盘”。
2. 询问米饭是否熟重；番茄炒蛋提示当前份量无法换算，并提供手填或保留未知。
3. 用户回答“米饭熟重，菜就按未知”，只修改对应字段。
4. 后端匹配适用的食品资料并计算已知部分；找不到适用资料仍保持未知。
5. 展示草稿及“汇总不完整”，用户确认后创建一次记录。
6. 用户说“米饭其实100克”生成原记录的更正预览，确认后在原证据上重算，
   不新增一顿午餐、不覆盖其他条目、不删除营养依据。

## 5. 模型工具清单

本模块确定为6个只读查询工具和4个准备工具，共10个模型可见业务工具。
这是设计契约，不是已经注册到项目中的工具，也不是整个项目的工具总数。
原有画像、反馈、菜谱详情、安全工具继续复用；每种意图只暴露所需子集。

### 5.1 只读查询

| 工具 | 关键参数 | 返回契约 |
| --- | --- | --- |
| `search_foods` | query、food_kind、适用生熟状态、limit | 本人可用公共/个人食物候选、稳定ID、来源/版本、计量口径及可用营养依据 |
| `get_meal_plans` | start_date、end_date、可选餐次/plan_id、cursor | 本人计划餐次/条目、份量、版本和有效已吃关联；旧整菜口径明确 |
| `get_diet_logs` | start_date、end_date、可选record_id/餐次/食物、cursor | 本人有效实际条目、数量、快照来源、版本和缺失情况 |
| `get_nutrition_summary` | start_date、end_date、day/week粒度、营养字段 | 确定性实际汇总、逐字段区间与完整度；不重复返回全部饮食原文 |
| `get_nutrition_targets` | start_date、end_date | 对应日期的有效目标、版本、生效范围、缺失目标 |
| `get_diet_deviation` | start_date、end_date、plan_id可选 | 已计算的计划/实际/目标对比、可比性和缺失原因，引用参与计算的版本 |

查找用于更正/恢复的已删除本人记录必须显式使用`include_deleted=true`，
仅允许更正/恢复意图且不返回已彻底清除的正文；汇总始终排除软删除和未确认草稿。
记录/计划查询的按ID和按日期参数使用互斥schema；按准确ID读取不要求模型猜测日期，
仍执行本人归属校验，按日期查询才应用日期范围上限。
日期含义由后端统一，用户身份、权限和查询预算不在模型可填写参数中。
单次明细/计划查询最多31天、每页最多50条；汇总/目标/偏差查询最多366天，
食品搜索最多20个候选。更大范围分页/分段时仍受整轮工具步骤、Token和返回大小限制；
预算不足明确说明只查询了哪一段，不能宣称已看完全部历史。
所有工具继承现有工具超时、响应大小与权限边界，不为上述上限放宽旧保护。

### 5.2 写入准备

| 工具 | 可选操作与必要参数 | 仅允许产生的结果 |
| --- | --- | --- |
| `prepare_intake_draft` | create/revise/discard；来源消息/授权media_id/计划或记录引用、字段证据、可选draft_id和base_version | 本人草稿、澄清项、解析任务或记餐预览；计划标记已吃/再吃一次也走此入口 |
| `prepare_diet_log_change` | correct/delete/restore；准确record_id、base_version、对应操作字段 | 实际记录更正、删除或恢复预览 |
| `prepare_meal_plan_change` | create/update/delete/copy；对象引用、版本、日期餐次和对应食物条目 | 计划新增、编辑、删除或复制预览 |
| `prepare_target_change` | set/correct/stop；目标数值/区间、生效日期及受影响目标版本 | 目标设置、更正或停用预览 |

各工具操作采用按action区分的严格schema，不提供任意patch路径、
数据库字段或可执行表达式。无关操作参数拒绝，不忽略后执行。
`prepare_intake_draft`的放弃草稿不删除已确认实际记录；确认后的修改只走记录变更。

准备工具会持久写草稿/预览，应在ToolRegistry标为受限写权限，
只能访问草稿和预览仓储，不能持有“提交实际/删除记录/改目标”的执行权限。
准备本身不要求先确认一次，否则会形成“确认生成预览，再确认保存”的双重流程；
最终写入仍由现有确认入口调用受权应用服务，模型工具列表没有`commit/approve`工具。
准备工具的幂等仅防止重复草稿，不代表已获正式业务写入授权。
放弃/改写已有草稿也需归属、版本和来源校验；任意自然语言不能放弃其他会话未选中的草稿。

现有`create_meal_plan`等已确认写入路径保留兼容，但新饮食意图只暴露相应prepare工具；
旧ToolExecutor不能绕过确认执行，新旧入口最终共用同一应用服务、预览校验和事务约束。
个人食物维护、数据导出和媒体清理由页面及API服务实现，不必为每个页面按钮新增模型工具；
若后续明确增加聊天操作范围，需记录工具契约变更，不能暗增任意通用写工具。

## 6. 模型输入与隐私边界

模型输入按任务装配：当前问题、必要近期双方上下文、选定草稿投影、
相关画像限制、当前可用工具schema及本轮所需工具结果。
不启动时全量加载饮食历史；数据库是权威，不把会话摘要当作实际记录或营养来源。
查询结果携带`scope/as_of/record_refs/versions/completeness/truncated`，
scope包含实际覆盖的本人日期范围、过滤条件和分页位置。
字段筛选和去重后仍超预算时先缩小/分页，不能静默截断关键数值再生成完整结论。
多个工具对比同一批数据时记录版本；有并发变更导致版本不一致则重新读取相关范围。

用户问“晚餐怎么安排”时可以读取已明确日期的当日摄入和目标，
不默认读取几个月饮食明细；每周分析优先汇总而非逐条原文。
用户删除记录后本轮缓存与后续上下文按删除代次失效，历史摘要不重新创建该记录。
上传图片仅在本次授权解析任务送视觉模型，日常营养汇总不附带全部历史照片。
图片内容、用户食品备注和工具文本均是资料，不能注入新工具权限或改变确认规则。
Trace只留工具名、记录引用、范围、版本、结果状态、耗时与用量；
当前确认节点会记录完整pending_tool_calls，新增饮食路径必须做定向脱敏投影，
同时检查工具结果、错误、检查点和模型请求日志，不能只在UI隐藏敏感数据。

## 7. 实现接点

本节是实现清单，不表示本轮已修改这些业务文件。

- `domain/enums.py`、`agent/contracts.py`：新增饮食查询/实际/计划变更/目标变更意图；
  独立`IntakeExtraction`及带来源的字段结构，不把实际数据装入推荐`IntentSlots`。
- `agent/state.py`与记忆投影：保存当前草稿/预览引用、版本、选定事件和待澄清字段；
  权威草稿留在数据库，避免整份私有记录反复进入检查点。
- `agent/agents/intent.py`和Planner：区分否定、假设、第三方及混合事件，
  仅使用对应意图工具白名单；不能依赖提示词作为唯一写入保护。
- `application/diet_service.py`、`intake_service.py`：实现证据校验、相对日期解析、
  草稿补丁、资料计算、预览生成、一次确认和幂等提交。
- `tools/local/`及注册表：10个工具的独立schema/结果模型/权限与有界返回；
  不把模型参数中的来源ID直接当已核验数据。
- `agent/nodes/confirmation.py`、`application/chat_service.py`及持久确认路径：
  绑定预览版本/哈希，处理编辑后的失效确认，拒绝时答复准确指明取消对象；
  正文“已保存”必须来自正式提交回执。
- API、`web/src/types.ts`、`lib/api.ts`、聊天页及饮食编辑器：
  共用预览组件、来源/未知提示、字段级编辑和一次确认，确认后刷新同一记录来源。
- 数据库迁移、内存适配器、Fake网关、测试夹具、真实解析评测集、
  取消/恢复与浏览器验收脚本同时更新；保持旧推荐和已保存聊天可读。

## 8. 会话验收矩阵

以下为必须实现的测试场景，不是当前已通过的测试。

| ID | 输入或故障 | 必须结果 |
| --- | --- | --- |
| C01 | 明确本人已吃、日期、餐次与数量 | 生成准确草稿，未确认不计入统计 |
| C02 | “明天想吃”“怎么做”“如果吃” | 分别计划/问答/假设，不写实际 |
| C03 | 第三方食用或主体不明 | 不自动写本人，必要时澄清 |
| C04 | 否定或纠正已吃事实 | 修改草稿或准备原记录变更，不新增负份量 |
| C05 | 同句两食物、不同数量单位 | 逐条绑定，不能串量或默认补份数 |
| C06 | 未说日期、无餐次、未知重量 | 日期默认明确展示、补餐次，允许明确保留份量未知 |
| C07 | “半盘”“一盒”“两人吃” | 没有依据不得转换成确定克重或平均分配 |
| C08 | 生熟不明、标签kJ/每份歧义 | 澄清或未知，不错配营养口径 |
| C09 | 用户多轮改量/删项/人工锁定 | 只更新指定字段，旧预览失效，不覆盖其他条目 |
| C10 | 同名食物多个、多个活动草稿 | 先选择对象，不猜测“那个” |
| C11 | 今天的请求排队到明天、Worker重启 | 日期锚点保持提交时，不漂移 |
| C12 | 草稿期间闲聊、换页、刷新或换会话 | 草稿保留、重新加载验版本，不自动确认 |
| C13 | 普通新记餐或实际记录后再推荐 | 不继承上一顿数量，不把食用当偏好或目标 |
| C14 | “好”、多预览“确认”、模型伪造批准 | 不直接提交，绑定唯一明确的有效预览 |
| C15 | 两标签不同版本确认、迟到解析 | 冲突显式返回，原更正不被旧结果覆盖 |
| C16 | 重复确认、响应丢失后重试 | 一份正式记录，原回执可恢复 |
| C17 | 查询、图片或草稿引用属于其他用户 | 服务端拒绝，不泄露记录内容 |
| C18 | 未记录、部分未知、超范围分页 | 明确完整度和已查范围，不按零或完整数据解释 |
| C19 | 用户撤销草稿、已确认记录再说取消 | 前者放弃草稿；后者准备删除，不声称已自动撤回 |
| C20 | 照片不清、模型失败、配额不足 | 保留可编辑草稿或明确失败，不伪造入账成功 |
| C21 | 一句同时过去实际、未来计划或目标 | 分对象/日期/预览，无混合自动提交 |
| C22 | 删除后历史消息/摘要仍提到旧记录 | 不复活数据，引用失效，后续查询排除 |
| C23 | 查询结果写入Trace或确认日志 | 仅保留必要引用和状态，完整明细/图片不泄露 |
| C24 | 新旧计划工具、确认和恢复兼容 | 同一授权和事务边界，旧接口不成为绕过路径 |

契约检查包括恰好10个业务工具、action判别schema、字段来源、权限、
草稿/预览状态转换及与主方案一致的期限/快照规则。
实际实施后补自动化测试，再跑后端、前端、外部存储、真实模型及浏览器验收；
文档场景数量不等于测试通过数或模型准确率。
