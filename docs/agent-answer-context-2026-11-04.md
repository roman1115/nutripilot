## 已实现

1. 意图调用增加本轮 `answer_task`：任务目标、通用/菜品上下文、指代对象、
   推荐数量和相对营养偏好。它不并入长期饮食条件。
   接受空指代，纠正任务字段误放入饮食槽位，但拒绝冲突或非法字段。
2. 指定替换只排除被替换的菜，不把拒绝的菜名存成排除食材。
   “脂肪太高，换一个”可保留高蛋白等条件，并比较已有配方的整菜脂肪估算。
3. 普通推荐检索成功后停止重复规划。Agent 根据候选和本轮任务自行选择，
   事实规范化不再自动补齐三张卡片或拼接个性化理由。
4. 生成携带近期原始消息，不重复传同一历史摘要；历史生成理由不能作为事实。
   通用原理/失败补救不携带旧菜谱，避免旧步骤污染当前问题。
5. 首稿和修订共享任务指令；修订读取证据记录及具体问题，
   不再重复携带全量工具结果。保留完整原始数据用于数值和安全校验。
6. 审核材料保留食材别名、来源状态、整菜口径、不确定区间和必要步骤条件，
   去掉重复来源链接及无关营养项。其他候选保留营养供限定范围的比较取证。
7. 程序从原始数据计算相对脂肪差值和百分比，生成 `computed:<meal_id>` 证据；
   仅在单一基准、有限非负数值、基准大于零且区间无不确定性时提供。
   差值不代表等份量、人均摄入或健康功效，Agent 自主决定是否解释。
8. Token 输入估算采用本轮提供方实际用量校准，并保留余量；
   原 24,000 Token、90 秒总预算和最多一次修订不变。
   结构化重试提供错误字段及可接受类型说明，不回传错误输入原值。

回答版本：`intent-v14`、`planner-v15`、`recommendation-v34`。
模型审核失败或预算不足时标记 degraded，不能把未审核原稿作为自然回答发布。
不满足相对脂肪要求的候选也不能在失败路径保留为已满足的推荐。

  原理和补救两轮均发布审核正文；没有把旧菜谱步骤作为补救事实。
  这证明上下文分离在该样例生效，不证明通用建议逐句正确。
- 8张推荐卡片的名称、四项营养、区间和来源与独立配方接口核对一致。
  本次对话记录71次模型尝试，已记录输入185,145、输出15,064 Token；
  固定反例、前期诊断和主入口冒烟另计，非全部调用成本总账。

人工复核仍发现以下问题，因此没有提升整体质量状态：

- 高蛋白午餐仍偏向整份蛋白总量大的1717千卡配方，个人午餐适用性不足。
- “为什么推荐第二个”的审核后正文出现“唯一适配 lunch”及“工具数据”等说法，
  其他候选字段在审核投影中不完整不能证明排他性，内部术语也不应进入用户回答。
- 原理/补救中仍有过强或前后不一致的定性说法，模型审核通过不等于人工质量通过。
- 无明确历史对象的澄清回答，审核引用 `verified_facts` 的非证据记录编号，
  被程序拒绝后仍会重复该引用，造成不必要的降级。

## 限制与后续

整体回答质量仍未验收通过。模型仍可能从菜名推断做法、夸大适用性或误判数量；
审核也可能漏判或误拒。合理的派生数值若没有程序提供的计算依据，仍会被拒绝。
预算校准是估计，并非精确 tokenizer；重复结构化重试仍可能耗尽预算。

本轮未修改前端，未运行前端构建或浏览器；未运行完整 40 场景、
CookHero 同题模型对照和生产压力测试。
下一步优先改善审核证据契约、其他候选信息的完整性和营养选择口径，
再用真实多轮复验；不通过追加固定正文模板或取消安全校验来掩盖失败。
