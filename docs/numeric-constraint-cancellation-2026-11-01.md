# 临时数值条件取消修复

验收日期：2026-11-01（Asia/Shanghai）。
范围为整菜热量上限、预算上限、准备时间上限、蛋白质下限的会话生命周期。
没有修改菜品数据、营养计算、前端、基础设施配置或通用空值合并规则。

## 原因与修复

- `IntentOutput` 原本剔除空值，`merge_slots` 也忽略空值；
  因而不能用模型返回 `null` 表达“取消此前限制”，否则旧条件仍在。
- 增加有类型、白名单和数量限制的 `clear_constraints`，只允许四类临时数值字段。
  不允许借此取消过敏、长期忌口或每日目标；省略和普通空值仍表示没有新要求。
- 意图识别使用 `intent-v9`，明确取消、保留、重新设置和否定取消的语义；
  食材条件继续使用原有操作，不扩大本轮范围。
- 状态解析将已取消数值保存为显式 `null`，而不是删除字段。
  新一轮复制状态、持久化和恢复时仍可区分“未指定”和“明确取消”。
  `clear_constraints` 只是本轮操作，不存入长期槽位。
- 工具执行边界移除已取消参数，即使 Planner 重新带入旧数值也不执行；
  已有新数值则覆盖旧规划参数，避免放宽限制后仍被旧的更严格条件卡住。
  未在槽位中指定的数值仍保留原有工具行为，过敏和忌口合并逻辑不变。
- Planner Prompt 更新为 `planner-v9`，要求按最终槽位执行，不从旧消息恢复取消条件。
  餐单路径区分“未指定每日目标”与“明确取消单菜限制”，不再因两个空值相等而移除取消标记。
- Fake 网关仅补充常用取消短语和否定形式，供离线回归使用；
  真实模式依然由模型进行受结构化契约约束的语义识别。

## 真实模型与重启验收

入口为 Web 5178/API 8006/MCP 8012，使用 `qwen-plus`、BGE、
PostgreSQL、Redis、Qdrant、HTTP MCP 和一个独立聊天 Worker。
使用独立验收用户及新会话，不修改已有用户画像或旧会话。

同一会话依次执行：

1. 推荐午餐，热量不超过 600 千卡、预算不超过 20 元、15 分钟内做好、
   蛋白质至少 10 克，并声明鸡蛋过敏。价格和时间未知，正确返回无候选。
2. 取消预算与准备时间，保留其他条件，恢复候选。
3. 不限热量，继续保留蛋白质下限与过敏事实。
4. 蛋白质也不限，四类数值条件均为显式 `null`。
5. 换一批，保持取消状态。
6. 重新设置 600 千卡上限，其余已取消条件不恢复。
7. 不要取消热量限制并换一批，600 千卡限制保留。
8. 重新加上 20 元预算，价格未知，正确返回无候选。
9. 完整重启本轮启动的 API、MCP、Web 与 Worker 后取消预算，
   保留 600 千卡和鸡蛋过敏，重新恢复候选。

9 轮全部完成，42 次实际 `qwen-plus` 调用，输入 97,350、输出 4,766 Token。
逐个核对模型名称、正数 Token、降级事件与快照，无模型降级；
对返回的 21 个推荐项按源配方复核保留的热量上限、蛋白质下限与过敏/忌口条件。
重启前队列没有待执行或执行中任务；重启恢复 16 条消息，续聊后为 18 条，
槽位与取消标记一致。没有清空数据库、删除数据卷或改写历史答案。
最终 Web HTTP 200，API `/health/ready` 为 `ready` 且 `chat_worker_ready: true`。

## 限制与后续

- 未重跑全量 40 个真实模型场景、浏览器交互、完整应用镜像构建或生产负载。
- 本轮不是任意条件编辑器；口味、菜系、饮食标签和每日目标的取消未扩展。
  食材原有取消操作保留，过敏及长期忌口不能通过本轮数值取消接口清除。
- 同一轮复杂反复修改仍依赖真实模型的语义识别，非法输出继续受校验和降级保护；
  本次小样本通过不代表任意自然语言都能正确识别。
- 不修改无关话题处理、历史错误回答或既有会话内容。
  当前仍为本地后台进程，不提供系统级自动重启守护。
