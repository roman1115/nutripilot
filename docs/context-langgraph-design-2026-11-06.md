# NutriPilot 上下文管理方案：LangGraph 状态与检查点版

日期：2026-11-06。
状态：混合裁剪、图状态/检查点记忆闭环与基础历史召回已实施并通过核心工程验收；
参数规模调优、画像版本及选择性遗忘等后续范围仍未完成。
当前实际范围、验证与限制以[实施验收记录](context-memory-acceptance-2026-11-06.md)为准。
以下保留完整设计目标，不表示每个后续目标均已交付。本次未重启现有服务。
本方案替代[上一版完整方案](context-refactor-design-2026-11-06.md)的实施建议。

## 1. 本版确定的选择

采用“LangGraph 会话状态 + PostgreSQL 检查点 + 完整消息归档 + 用户画像”。

- 近期原文、滚动摘要、摘要覆盖位置与本轮执行状态放进现有 `AgentState`。
- 复用现有 `FencedCheckpointer` 和生产 `AsyncPostgresSaver`，按图执行进度保存。
- 完整聊天原文继续保存在现有 `chat_messages`，用于页面、精确召回和记忆重建。
- 用户长期画像及显式反馈继续走现有存储与确认写入机制。
- 首期在图内通过摘要节点压缩；不新增独立摘要表、摘要任务表或后台摘要队列。
- 不引入 LangMem、记忆微服务或新的向量库，也不整体改写现有 Agent 图。

沿用此前确定的统一上下文、混合裁剪、80%触发、约60%目标及最近6轮目标。
本版实际调整的是摘要的权威存储和执行方式：从独立表/后台任务改为图状态/图节点。
这会让触发压缩的请求增加一次模型调用；不能同时宣称保留上一版默认后台压缩的延迟特性。

LangGraph 提供状态更新、消息 reducer、检查点和恢复机制；
业务仍需定义何时摘要、摘要什么、有效条件如何更新以及历史如何召回。
“接入检查点”不等于自动拥有正确的长期记忆或自动无损压缩。

项目未安装 LangMem。本方案不要求升级依赖。

## 3. 四类数据分别存在哪里

| 数据 | 权威位置 | 用途和恢复边界 |
| --- | --- | --- |
| 近期消息、摘要、有效会话条件 | LangGraph 状态及数据库检查点 | 正常执行和同一会话续聊；运行时载入内存 |
| 完整用户/助手原文、确认事件 | 现有聊天历史数据库 | 页面、精确召回、检查点缺失时重建记忆 |
| 当前图节点、待确认调用、本轮预算和执行归属 | 检查点与现有 run/执行存储 | 按既有执行契约恢复；摘要不赋予写入权限 |
| 跨会话稳定偏好、用户过敏原、厨具和反馈 | 现有用户画像及反馈数据库 | 按用户身份读取和显式确认更新 |

数据库不是退出进程时才写入的备份。检查点和原文归档是持续写入的正式记录，
用途不同；不另外维护一份可独立覆盖图状态的摘要记录。
`chat_threads.snapshot` 等现有结果快照是页面/结果投影，不作为第二个摘要写入入口。

开发模式的 `InMemorySaver` 只能在当前进程保留执行状态。
即使原文另有 SQLite 持久化，也只能据原文重建记忆，不能因此承诺图执行断点恢复。
首期不为演示模式增加新的检查点依赖；跨进程恢复验收针对生产持久检查点模式。

## 4. 状态契约

保留当前自定义 `AgentState`，仅为会话消息采用 LangGraph 原生消息 reducer：

```python
messages: Annotated[list[AnyMessage], add_messages]
```

这不是要求把所有业务工具返回改为聊天消息，也不改变当前模型网关的 JSON payload 协议。
历史中保存为 `system` 的确认决定，只能投影为低权限的历史事件数据，
不能直接转换成真正的模型系统指令。

建议会话字段：

| 字段 | 内容 |
| --- | --- |
| `messages` | 当前保留的原文消息，含稳定 ID、轮次、顺序及可用归档位置 |
| `memory_summary` | 一个结构化对象：摘要条目、覆盖位置/边界 ID、版本、来源、更新时间 |
| `history_loaded_through` | 已从归档检查和合并到状态的高水位；不是摘要覆盖位置 |
| `active_constraints` | 当前有效条件，含字段值、来源、适用人/任务/日期、操作和版本 |
| `context_snapshot` | 本轮采用的摘要版本、原文边界、画像/条件版本及增补来源 |
| `memory_epoch` | 用于识别重建、遗忘及旧检查点失效的会话记忆代次 |

`memory_summary` 至少包含：

```text
version
covered_through_position
covered_through_message_id
entries[]:
  kind, text, source_message_ids, subject, scope
updated_at
```

版本从0开始；摘要只覆盖连续、可定位且已经正式归档的完整前缀。
条目区分用户陈述、助手建议、决定、否定、更正、未决事项及讨论对象顺序。
正文和来源引用均需有界；覆盖边界表示“处理过这段历史”，不代表保留其中全部细节。
用户要求原话、具体数量或历史配方时仍需原文召回及工具复核。

保留现有 `user_message` 作为当前输入，但在模型请求中仅出现一次：
基础历史投影排除当前消息 ID，另用当前问题字段承载。
`recent_messages`、`conversation_summary` 可短期作为旧检查点读取兼容字段，
迁移后不再独立写入；澄清状态也不能再覆盖整段会话摘要。

每轮新输入仅提供：

- 当前用户消息的增量、当前 run/turn/trace 身份、日期。
- 必须重置的本轮字段，如工具结果、执行计划、错误、最终回答和本轮压缩尝试标记。
- 经明确规则更新的任务条件；长期画像从其权威存储读取。

收尾成功后记录 `memory_finalized_run_id`，新 run 清空该标记，
最终归档校验其与当前 run 相同；直接入口使用等价的稳定执行身份。
不再把 `new_agent_state()` 的全量默认值覆盖到已有会话。
省略的会话字段由检查点承接；不能把 `messages=[]` 误认为清空，
按 ID 合并和移除分别使用 reducer 与 `RemoveMessage`。
首次会话、普通新轮、确认续跑和同一 run 恢复必须分别构造输入。

## 5. 正常执行流程

普通新轮：

```text
身份/会话可用性/幂等校验 -> 保存当前用户原文 -> 增量图输入
-> memory_load -> 现有风险判断
-> context_prepare -> 必要时 summarize -> 冻结基础上下文
-> 意图 -> 规划/工具 -> 回答及现有输出校验
-> memory_finalize -> END -> 原文/结果/run 事务提交
```

被风险拦截的请求直接生成现有响应并进入 `memory_finalize`，
不为已确定拦截的请求额外调用摘要模型。

1. `memory_load` 按归档高水位合并新增消息，并补齐已有消息的归档位置，
   不每轮重读全历史。加载范围不重复注入当前问题。
2. 风险判断后，`context_prepare` 投影相关条件、画像及规则精简后的工具资料，
   检查窗口、整轮剩余 token 和期限。
3. 达到比例阈值、有可摘要前缀且预算足够时，进入 `summarize`；
   成功后重新计量，再冻结本轮基础快照。
4. 意图、规划、回答读取同一基础快照；阶段任务说明和本轮工具事实分别追加。
   按需历史召回作为有来源的增补记录，供后续阶段共同使用。
5. 所有对用户形成最终结果的路径进入不调用模型的 `memory_finalize`，
   按现有 `response_message` 相同规则保存实际最终响应及其稳定 ID。
6. 图结束且收尾已持久化后，沿用 `_finish` 事务保存助手原文、结果、run状态和事件。
   提交失败不提前报告完成，由原有恢复路径幂等补交。

本轮可能刚把最终回答写入图状态、尚未写入消息归档。
它可以供恢复使用，但在取得正式归档位置前不可成为摘要覆盖前缀。
下一轮 `memory_load` 按同 ID 补齐位置，不重复追加。

确认请求沿用现有调度：新的确认 run 承接原 `turn_id` 和已保存调用参数，
验证身份、确认 ID 和最新状态，只合并确认决定及必要执行字段，
不按普通新轮清空待确认调用。
请求确认、确认/拒绝事件、执行结果属于同一逻辑轮次；未解决确认组保持原文。
摘要不能替代工具调用、确认 ID、幂等键或真正的批准状态。

## 6. 近期原文保留策略

默认目标：最近6个已结束的完整用户轮次，加上当前未完成轮次。
确认、拒绝和追问关联事件按 `turn_id`、消息 ID 与实际状态归组，
不能简单取12条，不能按角色轮流猜测分组。

- 空间充裕时可以保留更多；超过8轮仅检查是否需要压缩，不独立触发模型调用。
- 当前问题、未完成确认组、当前选中对象及安全必需条件必须保留。
- 需要压缩时优先处理6轮以前的完整前缀，不能跳过中间原文后直接推进覆盖位置。
- 若保留6轮仍超额，先精简工具与召回资料；仍无法容纳时，
  可在本轮唯一一次摘要尝试中纳入较早的已结束轮次，实际保留数需记录。
- 超长的单轮、原文依赖强的任务或不存在可压缩前缀时，不强行宣称能保住6轮；
  无法合法容纳则明确缩小资料范围或停止本次模型调用。

消息退出常驻状态的条件是：成功摘要覆盖，且相关检查点保存成功。
规则投影可以不加载无关工具对象，但不能把“未摘要对话被静默丢弃”称为压缩。
不再用用户2000字符、助手3000字符的截断来伪装完整记忆；
API当前4000字符合法输入上限仍保留。

## 7. 混合裁剪与压缩触发

顺序固定：

1. 规则精简：筛选本轮相关工具对象、去重、提取必要字段、减少召回候选。
2. 对需要长期承接的旧完整对话做语义摘要。
3. 对最终序列化请求重新计量，确定能否调用。

必须保留相关菜品的来源/版本、食材、可选配料、单位、每份或整菜口径、
必要的营养范围及过敏事实。历史助手建议不得因摘要而升级成已验证工具事实。
本轮工具返回可以归档或留作执行证据，但不能逐轮无界重放。

预算定义：

```text
B = min(W - O - M, R - O - F - M)
u = I / B

W = 当前实际模型上下文窗口
R = 整轮剩余 token
O = 本次调用输出预留
F = 后续必要调用的保守预算，包含重复输入
M = 估算误差余量
I = 本次完整序列化输入，包括系统、schema、工具定义及全部上下文
```

模型窗口以当前配置/供应商能力为依据，不凭模型名称猜测。
不能只统计 `messages`，也不能把模型窗口直接当整轮可花费预算。

| 条件 | 行为 |
| --- | --- |
| `B <= 0` | 不计算比例，不启动新的压缩调用，进入现有预算降级路径 |
| `u < 80%` | 通常直接执行，不因轮数独立压缩 |
| `80% <= u <= 100%` | 有可压缩前缀且预计节省有意义、预算允许时压缩 |
| `u > 100%` | 不能直接发送原请求；合法精简/压缩后必须重新通过预检 |

压缩后目标约60%，不是必须达成的硬保证，更不能通过删除关键条件“达标”。
首期只在普通新轮的 `context_prepare` 阶段尝试一次摘要，
不把工具循环反复路由回摘要节点。工具返回后及每个模型调用前仍重新预检；
通过更精确工具投影、有界查询或现有降级处理超额。
确认续跑不重新摘要未完成确认组，同样必须通过每次调用的预算检查。

摘要调用本身计入原有整轮预算和期限；调用前为摘要请求及其后续工作预留费用，
成功后重新计算 `R`、`B`。输入更短不代表总剩余预算更多。
若摘要失败且原请求仍合法可继续，则保留旧状态继续执行；否则明确降级。
不得再次递归压缩、重置截止时间、偷偷提升预算或丢掉未覆盖历史。

初值仍是80%/60%、最近6轮目标、整轮24000 tokens和90秒。
摘要目标大小应由候选前缀、当前预算与保留条目共同约束，不能让摘要无限增长。
上述参数均待真实对话和模型测量；不承诺固定压缩率或延迟。
回答后可做下一轮预算预测并记录指标，但首期不在后台调用模型；
下一轮按新预算重新判断，不沿用本轮已耗尽的 `R`。

## 8. 摘要如何可靠落入状态

摘要节点读取旧摘要、待处理完整前缀及当前有效条件，调用现有模型网关。
完成结构、长度、来源 ID 和覆盖边界校验后，一次节点更新返回：

```text
memory_summary = 新摘要 + 新覆盖位置 + 新版本
messages = 对该前缀每条原文的 RemoveMessage
```

新摘要引用的来源只能来自旧有效摘要和本次明确提供的消息，
不能生成不存在的消息 ID，也不能覆盖未提供的历史位置。
有效条件、确认执行状态由业务契约管理，不让摘要模型直接改权限。
连续摘要应保留更正与撤销的最终语义，不能把旧条件再次带回。

摘要和移除必须属于同一次节点更新，经现有包装检查点保存。
摘要模型失败、输出无效、失去执行归属或检查点保存失败时，
不得将这一轮视为已完成压缩、不得推进已持久化覆盖位置。
恢复时读取最后有效检查点及 pending writes，由框架执行进度决定续跑。

需要持久化保证的生产调用统一 `durability="sync"`，
不能只有 `astream_durable` 同步保存、其他入口却暗中承诺相同恢复级别。
同会话单写者继续依赖现有队列约束、run版本和 `execution_fence`；
这不是 LangGraph 自动替代了应用锁，也不是跨聊天表的数据库事务。

首期不让后台任务直接 `aupdate_state` 更新摘要。
这样避免后台修改正在运行的图，以及 `as_node` 意外改变后续节点。
以后若实测必须后台压缩，需要另行设计串行归属、版本与调度，不能直接复用旧提案。

## 9. 断点恢复与两次提交

区分“恢复同一执行”和“开始下一轮”：

- 同一 `run_id` 的检查点存在且 `next` 非空：按现有持久入口传 `None` 继续，
  不重新准备新轮、不重复提交用户消息、不重新清空本轮字段。
- 同一 run 的 `next` 为空且收尾完整：跳过模型和工具，重试最终归档事务。
- 新 run：按增量输入启动，仅重置本轮字段，承接会话记忆。
- 进程恢复沿用原截止时间、预算结算及尝试次数，不获得新的24000 tokens或90秒。

收尾节点必须覆盖推荐成功、澄清、范围拒绝、风险拦截、预算不足、工具失败、
待确认、确认通过/拒绝和取消/超时等已有结果路径。
直接/流式入口与 Worker 使用相同的稳定响应 ID 和文本投影规则，
避免状态里和页面上保存两种不同回答。

当前 `_terminate` 使用 `aupdate_state(..., as_node="budget")`。
新增收尾后必须同步修改：先读取并核对当前归属的最新状态，
调用同一个无模型收尾投影函数形成完整更新，
再以实际的终端收尾节点语义提交，使 `next` 正确结束；
不能只改图边后仍把尚待执行的收尾当作完成。
该异常路径、`next` 判断和归档时序必须专门测试。

| 崩溃位置 | 恢复原则 |
| --- | --- |
| 用户已归档，图尚未接受输入 | 用同一用户消息 ID 重放输入，不重复归档 |
| 摘要请求完成，节点结果未可靠保存 | 从最近有效执行进度恢复，可能需要重新请求摘要 |
| 摘要与移除已持久化，后续尚未执行 | 使用已保存摘要继续，不再次推进同一覆盖范围 |
| 最终响应已在检查点，归档事务未完成 | 按同一响应 ID 幂等补交归档和结果 |
| 归档事务已提交，但客户端未收到完成 | 读取现有 run/事件/结果，不再次生成回答 |

当前稳定 ID 包括 `{turn_id}:user`、`{turn_id}:response`、
`{turn_id}:decision`、`{turn_id}:confirmation`，优先沿用，
并对同 ID 内容冲突报错，不能默默覆盖不同内容。
`_finish` 需验证当前 run归属、终端 `next` 和收尾标记，不能提交其他 run 的快照。

检查点和消息归档不自动成为一个原子 SQL 事务。
上述幂等与补交机制保证可恢复的一致性目标，但模型外部调用不具备天然 exactly-once：
模型已完成而结果未可靠保存时，仍可能重复调用和计费。
已执行的写工具继续依靠现有幂等存储及确认契约，取消不会自动撤销写入。

## 10. 历史召回与长期记忆

历史召回复用现有消息数据库，补带稳定位置的范围、关键词、日期及对象关联查询。
返回少量原文、必要相邻消息和来源，不把所有历史重新塞回当前上下文。
首期不新增聊天向量索引，不扫描旧检查点充当历史搜索库。

- 默认查询当前可用会话。
- 用户明确询问其其他会话时，才查询本人可用历史，继续应用身份和回收站过滤。
- 对“你之前第三个建议”“那天的做法”等依赖原话的问题，优先召回相关完整轮次。
- 历史助手文本用于还原“当时说过什么”，当前营养、配方和安全事实仍回原工具核对。
- 召回额度与工具资料额度独立约束；缺少依据时明确询问，不能猜测。
- 如新增召回改变了意图理解，最多有界补判一次，并更新共同可见的上下文增补记录。

用户长期记忆仍存画像和反馈，摘要不能自动写回画像。
“今天不吃辣”保存在当前日期/任务作用域；
“以后都不要推荐香菜”走现有显式保存和确认流程。

会话条件与画像更新至少表达 `set/add/remove/clear`，带来源、适用人、日期和版本，
以支持替换、撤销和清空，而不是只做列表累加。
用户过敏原与食品自身过敏原分别管理，不相互推断。
发布前检查安全相关画像/条件版本；若已变化，按预算重新核对或终止该轮，
普通偏好变化可下一轮生效，不在同一轮悄悄替换基础上下文。

## 11. 重建、更正、遗忘与删除

旧会话的原文和稳定位置继续保留。
旧检查点缺少新字段时，在新一轮采用明确的兼容分支，从正式归档重建；
不能把原来的 `compact_messages` 拼接截断直接标成可靠滚动摘要。
待处理前缀若超出单次摘要预算，按有界范围重建并记录尚未覆盖的区间；
本轮不能完整取得必要信息时降级，不在一次请求中无限追赶全历史。

检查点缺失时可以重建会话记忆，但不能从自然语言摘要重建可执行的确认或批准。
存在未完成写入/确认且执行状态丢失时，沿用安全恢复或重新确认，
不凭聊天正文继续执行旧写工具。

用户更正后以新有效条件/画像为准，旧摘要不得覆盖它。
“忘记某条记忆”和“删除原文”应按实际请求分别处理：
不要求物理删除时，可在现有会话元数据记录失效来源和记忆代次；
加载、摘要、召回与重建均校验这些标记，避免旧信息复活。
新检查点不能自行降低记忆代次，恢复旧检查点也必须先检查当前权威元数据。
这些生命周期元数据不是第二份摘要正文，也不产生独立摘要任务。

若要求彻底删除敏感内容，必须处理原文、相关检查点及其他持久副本；
仅发 `RemoveMessage` 或重写当前摘要不算彻底删除。
选择性遗忘的物理清理采用受控重建：会话无活动任务时清理其旧检查点，
再基于允许保留的正式记录重建会话记忆，不用旧检查点继续执行未确认写操作。

沿用当前回收站与删除约定：有活动 run 时拒绝删除，不擅自改为直接杀任务删除。
回收站内停止执行和召回；7天到期清理需删除全部会话检查点和原文/run等记录，
沿用现有可重试清理流程。画像是独立数据，删除会话不自动等于删除画像。
普通恢复回收站会话也必须校验当前画像版本、失效来源和记忆代次。

旧检查点可能保留曾移出的原文，体积也会随执行历史积累。
实施前要测量当前 saver 实际占用；首期沿用会话整体清理，不直接删除仍可能恢复的检查点。
长期保留策略依据运行规模再决定，不能把状态列表变短等同于数据库已经变小。

## 12. 实施顺序与验收

第一步：建立会话记忆闭环。
完成状态字段/增量输入、正式归档合并、统一基础投影、图内摘要、
终端收尾、同步持久化、预算预检及旧会话兼容。
取消独立摘要表/任务的实施计划，先验证近期承接、原文覆盖和故障恢复。

第二步：增加有界历史召回。
补历史读取契约和适配器，处理位置、关键词、日期、对象来源和身份隔离。
不等同于引入另一个长期记忆服务。

第三步：补条件撤销、画像来源/版本及遗忘生命周期。
现有画像、安全条件及确认机制从第一步起继续保留，
增强字段与旧会话恢复、回收站及清理联动完成后再宣称长期记忆管理完整。

对应测试范围：

| 类别 | 必须验证的行为 |
| --- | --- |
| 状态与消息 | 同 ID 重试不重复，新轮不清空摘要，当前问题仅出现一次 |
| 完整轮次 | 双方原文、澄清、确认/拒绝成组，未完成确认不进入摘要前缀 |
| 摘要覆盖 | 旧摘要融合、来源校验、连续边界，失败不移除、不推进 |
| 预算 | 完整 payload，80%触发，100%硬限制，摘要费用和后续重复输入 |
| 多阶段承接 | 意图、规划、回答看见同一基础内容，指代与助手建议顺序可追溯 |
| 收尾 | 正常/失败/取消/确认路径的检查点消息与正式页面原文一致 |
| 持久恢复 | 摘要前后杀进程、终端归档前后崩溃、同 run续跑、预算不重置 |
| 并发和安全 | 旧 owner不能提交，串行同会话、跨用户隔离、回收站过滤 |
| 条件与删除 | 撤销清空、画像更正、旧检查点/摘要/召回不得恢复失效记忆 |
| 事实回归 | 不混旧配方，不丢单位/可选项/份数，不把助手文本当事实证据 |

优先扩展已有 `test_agent_state.py`、`test_agent_context.py`、
`test_conversation_history.py`、`test_graph_confirmation.py`、
`test_durable_chat.py`、`test_durable_processes.py`、`test_external_persistence.py`
及做法/营养对话测试，按风险新增必要夹具。
实现后运行相关 Ruff、mypy、pytest；若改动前端契约，再执行前端 typecheck/build。
真实模型、PostgreSQL 故障恢复、长对话质量和延迟必须分别运行并记录，不能由内存测试代替。

记录摘要触发次数、实际保留轮次、覆盖范围、估算/实际 tokens、
摘要耗时和失败、剩余预算、召回来源及恢复结果。
不把原文和用户敏感内容无界复制进日志。
