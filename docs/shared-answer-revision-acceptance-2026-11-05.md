- 保留共享主提示词与现有短任务说明，约束生成区分来源事实、程序估算、用户条件和通用建议。
  提示词明确详细做法不补包装克重、不因上轮营养话题继续追加配餐克重；
  实测遵循情况见下文，不将提示词要求当作模型已稳定做到。
- `prose_issues` 不再以数字集合不匹配直接否决正文，其余结构、来源、真实候选、
  医疗和过敏保证等确定性检查保留；所有维护中的调用及测试已同步。
- 新增内部 `answer_quantity_hints`，只从本次语义审核实际收到的来源及程序结果提取线索；
  不从slots、历史助手正文或未投影的State补依据。数字匹配也不直接判为正确。
- 使用Decimal进行质量、体积、时间和长度同量纲精确换算；营养显示取整只适用于
  已知营养字段，不扩大为配方重量、时间或任意数字的容差。
- 现有语义审核继续检查全文、中文数字、肯否/假设语境、跨对象和跨字段借数，
  不新增逐句引用契约、Agent或模型调用上限。
- 修订保留完整旧正文和有效卡片理由，仍最多一次；两稿失败、审核异常或预算不足时
  不发布旧稿。最终事实摘要与安全复查保持不变。
- 真实回归中进一步发现资料投影缺口：没有显式菜品ID时，当前成功的做法/营养查询
  可能被丢弃，或仅剩历史对象。已改为在没有显式目标时优先使用当前成功查询对象，
  无当前对象再回退历史展示；失败工具结果不作为审核依据。
  修改前新增回归实际复现2项失败，修改后3项全部通过，且原State不被修改。
- 完整HTTP对话进一步发现：意图已为做法查询，但模型给出 `context=general`，
  导致生成与审核仍清空菜谱并引入无关通用安全资料。现有任务规范化函数新增规则：
  `RECIPE_QUERY`、`NUTRITION_QUERY` 固定使用 `context=meals`，
  原通用问答仍保留general能力。新增2项测试在修改前复现失败、修改后通过；
  只规范意图已确定后的任务上下文，不重写意图识别或增加模型调用。

不新增600千卡或其他默认饮食限制，不改长期用户画像，不补造种子数据，

## 4. 真实模型方法

`scripts/verify_answer_quantities.py` 使用隔离State和最终OutputGuard，保存每次输入、
模型响应、审核结果、批准/降级结果与实际Token。固定草稿由脚本注入，审核使用真实模型；
反例连续两稿相同以验证不能放行，正例也检查每次决策，不能用第二次通过掩盖第一次误拒。
完整生成允许按既有流程修订一次，需另行人工阅读全文。
合成资料只用于测试，不写入菜谱库；报告标明自动检查与人工审核的边界。

原请求从 `.runtime/diagnose_recipe_grounding_2026_11_05.json` 的生成前State恢复，
保留11月4日原线程/轮次标识；原来源明确为1人份、豆腐只写1盒。
该历史报告保持原样；其同目录旧诊断脚本针对v50内部接口，不作为新版执行入口。
历史18次实验没有当前完整审核链路，不据此声称新版成本或总体质量优于v50。
