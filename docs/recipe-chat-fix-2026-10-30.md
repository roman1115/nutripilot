# 做法查询与回答可读性修复

验收日期：2026-10-30。仅描述本轮实际实现和验证，不代表整体模型准确率。

## 实际故障

原会话 `ac1962378d0549089f1776b1176ee34d`：

- 用户先发“推荐午餐”，得到三道推荐。
- 再发“给我西葫芦炒鸡蛋的做法”，仍得到三道推荐，没有食材用量和步骤。
- 卡片说明由后端强行覆盖为六项营养、投料重量、免责声明、过敏原和偏好匹配；
  范围使用通用浮点格式，出现过长小数。不是单纯的字号或模型措辞问题。

当时意图枚举和 MCP 都没有做法查询，而 100 道来源菜谱已经存有原始用量与步骤。

## 实现

- 新增 `RECIPE_QUERY`，接入 Intent/Planner/Fake、工具白名单、Supervisor 路由和澄清。
  `get_recipe` 复用菜名/编号验证及在用记录门槛；明确菜名在执行边界覆盖旧候选编号。
- 服务使用同一次载入的版本化 catalog，不偷偷使用其它目录的数据。
  MCP 返回原始食材、用量、步骤、过敏标注及来源版本、许可证和文件哈希。
  正式 HTTP 服务注册工具，已有认证、Schema、响应体和执行预算边界保留。
- 步骤由程序直接据实排版，不让模型编造、重写时长或火候，也不再展示推荐卡片。
  原文 Markdown 加粗转为普通文字；没有明确用量时如实说明。
- 保存上一轮实际展示顺序及最近查询菜品。“第二道”按顺序定位，
  多候选的“这个”先澄清；新轮显式清空澄清标记，避免一次追问污染后续对话。
- 卡片说明只保留有据偏好、约束匹配或主要食材；营养独立展示。
  文本中的营养数值保留一位小数，原始 API 数值及上下限不变。
  长计算说明移至引用的 `excerpt`，前端沿用已有“回答依据”折叠区域；
  整道菜估算、个人摄入边界和过敏提醒仍可见。
- 没有变更种子营养数据、人均换算、历史记录、Worker 数量或并发配置。
  来源原文若说明人数仍照实展示，不表示系统另行计算个人份量。

重跑浏览器：

```bash

  --executable "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
```
