## 发现与修复

1. 首次真实推荐在生成阶段触发 Token 上限：完整配方计算说明、食材来源反复进入模型。
   复用并完善工具结果投影，仅从模型上下文移除冗长说明和来源 URL，
   保留菜名、编号、食材、过敏原、整菜份量、营养范围、状态与标签。
   规划校验、营养补齐及最终引用继续读取完整原始工具结果，未删除原始事实。
2. 输入精简后，生成仍可能超过单次模型的 25 秒时限。
   独立诊断返回有效结构，但用了 31.10 秒、输入 4,254、输出 1,374 Token。
   Prompt 现在要求最多三道菜和简短理由；营养、来源和警告由程序补齐，保持原有时限。
3. 三餐规划同时发出三个检索请求，工具层又将每个扩成三餐，导致调用次数超限。
   工具边界现在按每个所需餐次选一个对应请求，缺少的餐次才复用首个请求，
   一日三餐只执行三次搜索；每次仍注入过敏和忌口约束。
4. 首轮固定推荐为 9/14：点名红烧鲤鱼被相似菜替代；价格/时间未知的空候选反复搜索；
   “不超过1千卡”误提取为 1000；换菜重复检索触发 Token 上限。
   现在成功检索后由 Supervisor 进入推荐（含空候选），不让模型无目的重搜；
   精确点名且在候选内的菜优先；明确千卡上限由确定性规则保留原数值。
   不添加库外菜品、不放宽过敏或未知价格/时间条件。
