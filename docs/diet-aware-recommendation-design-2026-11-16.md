# 实际摄入与下一餐推荐联动方案

设计日期为 2026-11-16。2026-11-18 经 xerina 授权实施，本地验收记录见文末。

本方案覆盖个人下一餐推荐的完整闭环，工作包只表示实施依赖，不代表精简产品版本。
饮食管理D01–D09的既有交付保持原状态；本方案是其上的推荐能力扩展。
原数据、份量、来源、确认和隐私规则以
[饮食管理实施基线](diet-management-implementation-spec-2026-11-11.md)为准。
本文件获认可后，实施前同步更新基线、工具Schema、样例与验收契约，
不以待评审文档提前修改已冻结的运行契约。

## 1. 交付结果

用户问“今晚吃什么”，系统能够读取本人当天记录、当日生效目标和相关计划，
结合偏好、禁忌及本轮要求，给出可选菜品/搭配、个人建议份量和解释；
可以修改份量、换一组、确认加入计划，吃后再确认记为实际。

不新增独立页面。聊天展示推荐，餐单承接安排，饮食记录承接实际与更正。
不要求用户先设置目标、称重、补齐所有营养字段或声明全天完整。
缺资料时仍给可用建议，只收窄可支持的数字结论。

## 3. 何时读取饮食数据

| 用户请求 | 处理 |
| --- | --- |
| “今晚吃什么”“结合今天吃的推荐下一餐” | 本人当日下一餐模式，读取相关摄入、目标和计划 |
| “明天午饭吃什么” | 读取明日生效目标和计划；不把今天的摄入扣到明天 |
| “推荐几道川菜”“番茄炒蛋怎么做” | 沿用通用菜品/做法路径，不强加个人当天差额 |
| “给朋友推荐”“这次不参考我的饮食记录” | 不读取本人饮食记录；遵守本轮明确的对象和限制 |
| “换一个”“份量减半” | 继承当前推荐对象与日期，重新读取有效数据并计算 |

日期使用现有消息提交锚点与用户IANA时区；排队、跨午夜和恢复不能改成服务器当天。
餐次不明确时先给“下一餐”建议；需要保存计划且仍无法确定日期/餐次时才询问。
旧`late_snack`在饮食餐次接口映射为`snack`，保留原话，不新增第五餐次。
“再推荐”本身不意味着新增实际记录，也不意味着自动覆盖已有计划。

## 4. 一次读取的推荐上下文

建议新增只读工具`get_recommendation_context`，归属`diet:read`。
原10个饮食工具继续负责详细查询与准备操作；本次只增加这1个聚合读取工具。
个人推荐路径由编排保证调用，不让模型随意省略；本轮禁止参考记录时不调用。

输入草案：

```text
local_date?: YYYY-MM-DD   // 缺省为消息锚点当地日期
meal_type?: breakfast | lunch | dinner | snack
```

不接收`user_id`、客户端营养总数或任意SQL/过滤表达式。
身份、消息锚点与读取时间来自受信执行上下文。

返回类型必须包含：

- `local_date/timezone/as_of/diet_epoch`及上下文摘要版本。
- 当日当前有效实际记录的六项营养汇总：值或已知小计、字段覆盖、未知原因、
  来源类别及可追溯引用；不把整批记录正文塞进提示词。
- 当日生效的四项目标区间、目标引用及版本；缺目标明确为空。
- 当日计划的餐次、个人份量、营养及关联实际的执行状态；多个计划保留区别。
- 日完整度声明，以及可用于本轮的条件差额与限制原因。

在同一个本人事务中取得一致快照；服务端聚合全部适用记录，
不能把分页第一页或`ReferenceOnly`对象当作完整数据。
提示词中的明细可有界裁剪，但汇总和覆盖情况不能因此丢项；
裁剪需显式标识，详情仍由原查询工具获取。

“当前记录”指读取时已保存的实际记录，不含草稿、预览、软删除或未执行计划。
明确带未来发生时间的记录不当作截至当前已吃；无时间记录按当日本地日期纳入，
注明无法确定餐内先后。历史更正沿用记录所属日期，不随用户旅行自动挪日。
未来推荐不计算实际摄入差额；上下文查询失败与“无记录”分别处理。

## 5. 差额与不完整数据规则

这里是“根据当前记录安排下一餐”，不是“判定一天是否达标”。
保留原`open/complete/no_intake`语义，不要求吃晚餐前先声明全天完整。

对已有记录且该字段全部可算的情况，按区间计算：

```text
条件差额 = [目标下界 - 已记录上界, 目标上界 - 已记录下界]
```

差额允许负值，单独使用有符号类型，不套用只能非负的摄入区间模型。
即使条目字段齐全，`open`日也只说“按当前记录估算”，不作全天正式达标结论。
其他规则：

- 某字段有未知条目：只给已知小计和缺项，不给该字段的完整剩余额度。
- 没有记录：不是摄入为0，不计算精确差额；全天`no_intake`声明也不改造成
  “截至午饭前未吃”的新含义。与下一餐场景矛盾时说明限制，继续提供候选。
- 来源是照片模型估算：允许参与带标识的估算；保留来源，不升级为已验证。
- 无目标：按偏好、禁忌和可支持的搭配推荐，不自动发明每日目标。
- 计划未吃：与实际分列，不扣作已吃；已关联实际只统计实际一次。
- 同日同餐有多个计划或多次实际：不按菜名猜关联或擅自选择要覆盖的计划。
- 差额不是下一餐必须吃完的预算；不默认固定三餐百分比，不强求四项同时达成。
  用户明确给出的“这一餐”约束单列，不混入旧的“单道菜热量上限”字段。
- 当前记录已高于目标时仍提供正常可选餐食，不输出“不吃下一餐”或补偿性节食建议。

## 6. 模型选菜，程序计算个人份量

执行顺序固定为：

1. 识别本轮场景，取饮食上下文、画像和必要反馈。
2. 复用`search_meals`检索，按需要用`search_foods`补充有资料的主食/个人食物。
   用户禁忌、过敏与本轮硬约束沿用现有校验，不由模型文字保证替代。
3. 模型从返回候选中提出1–3个可选方案，每个包含食物引用、建议数量和选择理由。
   每个方案是一次选择；同一方案内的多个食物才相加，不能把备选方案相加。
4. 服务端重新解析来源，复用`calculate_nutrition`与汇总函数，
   计算个人份量、组合营养及条件比较；模型不提交最终营养合计。
5. 校验引用、份量依据、禁忌、硬约束与解释中的数值。
   数字和卡片由程序核定结果生成，模型只写符合证据的解释。
6. 无效提议最多定向修正一次；仍失败时返回已验证可用候选及具体限制，
   不把违反硬约束的方案标成合格，不因某项资料缺失让整个推荐不可用。

份量沿用既有类型：

- 质量/质量区间：只有每100克资料、食物状态及可食部口径匹配时才量化。
- 份数：必须有服务端可核对的每份依据。
- 菜谱：优先用`recipe_fraction`，如“按原配方做一批，建议你食用其中1/2”。
  这是推荐的食用安排，不是声称原配方天然等于两人份。
- 熟重：有整批成菜熟重才能按本人熟重换算；不拿原料重冒充熟菜重。
- 无适用资料：保留数量描述与未知营养，仍可推荐，不猜每100克营养。

建议份量与用户实际食用量是两个事实，建议不会自动入账。
不能靠把份量压到极小来伪装满足热量约束；推荐解释及真实场景验收须检查实用性。
候选库支持时可组合主食和菜；只有单菜或角色不明时标为一道菜/部分搭配，
不能声称已提供营养完整的一餐。缺钠/纤维不排除其他字段可用的候选。

## 7. 结果契约与界面

在`FinalResponse`增加独立`personal_meal_options`结构；旧`recommendations`继续表示整菜。
个人推荐至少包含方案ID、日期/餐次、各食物的可解析引用和建议`Quantity`、
程序核算的个人营养、字段覆盖与来源、上下文版本、解释及限制。
数值使用现有十进制字符串/区间契约，不经旧浮点字段往返。

聊天呈现三层信息：

1. 简短依据：“结合今天已记录的饮食和当前目标”；有缺项时就近提示限制。
2. 1–3个方案，展示菜名/搭配、本人建议份量和个人估算营养；
   整菜做法及整批营养放详情，标明口径。
3. 复用现有样式提供调整份量、换一组、加入计划及查看依据入口，
   可跳转饮食记录更正或目标管理；桌面和手机都可完成。

不加额外看板或永久开关。用户本轮明确不参考记录即可。
份量调整由程序即时重算，不必为每次加减重复调用模型。
无目标、未知营养、只读查询失败、无适用候选分别有明确状态；
失败不能展示为“已根据你的摄入推荐”。

## 8. 计划、实际、并发和历史联动

- 点击加入计划或聊天中明确提出保存，才准备预览；
  选择本人既有计划或创建计划，目标餐次已有内容时明确追加/替换。
  服务端通过本人已完成响应的方案引用读取候选，再解析食物及份量，
  不信任客户端回传的营养值、他人的响应ID或过时来源。
- 准备与最终确认继续复用`PlanService`及现有hash、版本、期限和数据库幂等；
  正式计划保留个人份量和证据快照。普通推荐本身零正式计划/摄入写入。
- “标记已吃”继续复用计划转实际，实际日期、餐次、份量可改，再确认入账。
  重复点击不重记，明确“再记一次”保留既有语义。
- 生成完成前复查`diet_epoch`、相关画像/食物版本。变化时最多重读重算一次；
  持续变化则标明读取时点，保存前必须重新核对，不无限循环。
- 预览后饮食变化影响推荐理由时，显示更新依据并重建预览再确认；
  相关对象版本冲突按既有规则处理。无关对象变化可更新上下文，
  不无条件阻塞整次操作。
- 已完成历史回答保留当时快照，不后台改写；再次推荐须读取最新数据，
  不从历史聊天数字还原当前摄入或已停用目标。
- 新推荐涉及的私人数字与引用纳入既有记忆替换、脱敏Trace、导出与清除范围；
  持久推荐结果及可恢复任务不得在清除后重新把已删除记录送入模型。
  普通历史消息只按既有用户可见历史/清除规则处理，不能伪称从未保存过。

## 9. 示例

假设本人当天热量目标1800–2000kcal，当前记录的热量全部可算，
合计1100–1200kcal，尚未声明全天完整。

程序可得“按当前记录估算，距当日目标的差额为600–900kcal”，
但不把它宣称为精确剩余额度，也不要求晚餐必须覆盖全部差额。
实际候选和个人份量仍须从目录证据计算后展示，示例不编造具体菜品营养。
如果其中一项摄入热量未知，则不展示600–900这个区间，
仍可根据已知记录、偏好和候选营养给出建议。

## 10. 实施顺序与验收

| 工作包 | 完整交付内容 |
| --- | --- |
| R01 契约与计算 | 场景/日期、聚合工具、区间和覆盖规则、个人推荐结果；同步基线、Schema与样例 |
| R02 Agent接线 | 路由/工具白名单、必需读取、检索与建议份量、程序核算、证据/数值/安全校验 |
| R03 用户闭环 | 聊天卡片、调整/换组、计划选择与冲突、预览确认、计划转实际及恢复 |
| R04 隐私与验收 | 历史/记忆/清除、并发与失败路径、工程回归、真实模型和桌面/手机验收 |

R01–R04全部完成才称本模块完整交付；真实流式输出是独立后续模块，
本功能复用当前持久Worker、进度事件、取消与恢复。

| 验收项 | 必须证明 |
| --- | --- |
| A01 数据确实参与 | 同一问题更正当天摄入/目标后，输入投影、个人营养比较和解释使用新值；不强求菜名必变 |
| A02 口径正确 | 整菜/个人/组合/备选互不混算；Decimal区间、来源、舍入及更改份量结果可复核 |
| A03 缺资料仍可用 | 无记录、无目标、open日、部分未知、照片估算均可给适用建议；未知不补0 |
| A04 日期和隔离 | 时区、跨午夜、未来目标、历史更正、本人归属与第三方场景均正确 |
| A05 计划不当实际 | 未执行计划不扣已吃；关联实际不双算，多计划/追加/替换/再记一次语义正确 |
| A06 写入安全 | 推荐零正式写入；预览确认、重复/双击/恢复不重复，过期和版本冲突可处理 |
| A07 变化与故障 | 生成中修改、来源失效、查询失败、模型无效输出及中断恢复有可验证结果 |
| A08 隐私 | Trace/摘要不泄露完整私有正文；删除/清除后新推荐和恢复任务不复用已删除事实 |
| A09 原功能回归 | 通用推荐、做法、营养问答、旧整菜餐单和饮食D01–D09相关路径通过 |
| A10 实际使用 | 桌面/手机完成推荐→调份量→确认计划→吃后调整→确认实际→更正后再推荐 |

验证分三层：确定性计算/契约测试，API/Worker/持久化及浏览器集成，
现有真实千问的冻结场景与逐项人工复核。Fake结果只证明工程流程。
真实场景至少覆盖摄入/目标变更、未知、估算、禁忌、未来日期、换餐和计划转实际；
同时保留失败样本，单列计算正确率、引用正确性和建议实用性，不合称“营养准确率”。
验收运行Ruff、mypy、pytest、Schema校验及前端typecheck/build；
真实服务和模型只在实际执行后报告通过，并更新状态页与专项证据。

## 11. 本轮明确边界

本方案不自动设置医疗营养目标，不新建私人食谱CRUD，不扩充无依据食物库，
不依赖流式改造、不部署，也不把单次目标贴合声称为全局最优或健康保证。
